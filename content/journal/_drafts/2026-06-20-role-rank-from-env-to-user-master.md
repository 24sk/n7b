## env でロールを配るのをやめた話

社内向けに作っているスケジューラ「skedachi」で、ダッシュボードや「太鼓判」(称賛機能) を見られる人を判定するロジックを書き換えました。今までは環境変数にメールアドレスを並べて「この人は manager」「この人は executive」と区分けしていたのを、ユーザーマスタ (組織図) の `雇用形態` から自動で導く形に変えています。

この記事では、なぜ env で持つのをやめたのか、移行で何を捨てて何を足したのかを順に書きます。同じように「環境変数に運用情報がにじみ出てきた」プロジェクトの参考になれば。

## なぜ env から外したかったか

もともとの実装はこうでした。Nuxt の `runtimeConfig` に `NUXT_ROLE_EMAILS_EXECUTIVE` / `MANAGER` / `LEADER` を持ち、Google OAuth ログイン時に `resolveUserRole(email)` を呼んで `users.role` を確定させる。シンプルで、最初は十分に機能していました。

ただ運用が進むにつれて、env が「秘密」と「組織情報」の二重生活を送り始めます。

- 役員が代わるたびに `.env` を書き換えて再デプロイする
- 組織図 (Notion 側のマスタ) と env が二重管理になり、ズレる
- 「この人なんで太鼓判押せないの?」が env を見ないと分からない

秘密鍵を入れる金庫に、住所録まで突っ込んでいるような状態です。本来マスタを見れば分かる話を、デプロイの都合に縛りつけてしまっている。

## マスタから導出するルールを 1 箇所に集める

方針は単純で、Notion 組織図のローカルミラー (`org-members.json`) にある `雇用形態` を見て役職ランクを決めます。

- 代表取締役 → executive (太鼓判が押せる)
- 役員 → manager (一推しが押せる、ダッシュボード閲覧可)
- それ以外 → member

マッピングは `shared/roles.ts` に `EMPLOYMENT_TYPE_ROLE` という定数と `roleFromEmploymentType()` 関数で集約しました。「雇用形態から役職ランクへの変換表」を 1 枚作って、OAuth ログインハンドラと組織マスタの seeder の両方からそこだけを呼ぶ。

```ts
// shared/roles.ts
export const EMPLOYMENT_TYPE_ROLE = {
  代表取締役: 'executive',
  役員: 'manager',
} as const

export function roleFromEmploymentType(type: string): Role {
  return EMPLOYMENT_TYPE_ROLE[type] ?? 'member'
}
```

レゴブロックで言うと、今までは「赤いブロックはここ、青はここ」と組み立て手順書 (env) に書いていたのを、「ブロックの形を見れば置き場所が決まる」というルールに変えた感覚です。手順書を書き換える必要がなくなりました。

ダッシュボードのガード (`middleware/admin.ts`) は manager 以上で通す形に揃え、env 由来の `resolveUserRole` ユーティリティとそのテストは丸ごと削除しています。

## 学び: 「leader (推し)」をどう扱うか保留にした

移行作業でひとつ判断を保留した部分があります。

社内には executive / manager / leader / member の 4 段階がありますが、`雇用形態` には leader に相当する区分がありません。代表取締役と役員は明確に列があるのに、リーダー職は雇用形態という軸では切れない。

最初は「とりあえず付与なし」で実装を進めたのですが、レビュー段階で「一旦変更しなくて大丈夫です」と差し戻し、leader の扱いだけは現状維持にしました。マスタに無い情報を無理やりマスタから引こうとすると、別の二重管理を生んでしまう。中途半端に自動化するくらいなら、leader 列を組織図側に足す日まで保留する方が筋がよさそうです。

もう一つ気付いたのは、テストの置き方。env 由来のロジックを消すときに、対応するテスト (`resolve-user-role.test.ts`) も一緒に消して、マスタ由来の新しいテストを同じ位置に置きました。「ロジックを消したのにテストだけ残る」が一番厄介なので、削除と追加はセットで行うのを徹底しています。

## まとめ

- 認可情報を env から引き剥がし、ユーザーマスタの `雇用形態` から導出する形に変えた
- 変換表は `shared/roles.ts` に集約し、ログイン時と seeder の両方から同じルールを呼ぶ
- マスタに対応する列がない区分 (leader) は、無理に自動化せず保留
