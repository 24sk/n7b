## 結論から: shiki は plaintext に色を付けない

記事ページのコードブロックを VS Code 風にしようと shiki (Markdown を色付きで描画するライブラリ) を入れたところ、言語を指定しないコードブロック (` ```text ` や言語なしのフェンス) が暗い背景にほとんど溶けて見えない、という現象に遭遇しました。

原因は単純で、shiki は言語別のトークン (キーワード・文字列・コメント) に色を付ける仕組みなので、**言語が分からないテキストには何も色を塗らない**。結果として CSS の `color: inherit` が効き、本文用の暗いブラウン文字色を継承して、暗背景の中に沈んでしまっていました。

この記事は、その現象を見つけてから一行で直すまでの流れと、似たような "テーマを当てたのに読みにくい" 状況を切り分ける考え方をまとめます。

## 何が起きていたか

N7B が触っているプロジェクトでは、Markdown のレンダリングを Nuxt UI の `ProsePre` が担っており、そこに shiki の `dark-plus` テーマを差し込んでいます。導入直後、言語付きのブロック (TypeScript や Vue) はきれいに色が乗ったのに、説明用に書いた言語なしのブロックだけが「黒地に焦げ茶」で読めません。

ブラウザの開発者ツールで該当要素の computed style を見てみると、文字色が `--color-ink` (本文の暗色) のままでした。shiki が `<span style="color: #xxxxxx">` を一切付与していないため、外側の prose スタイルがそのまま勝っていた、という構図です。

メタファーで言うと、**「色鉛筆セットを買ったのに、塗り絵の下絵がない部分は白いまま」**という状態に近い。shiki は下絵 (トークン) があるところしか塗ってくれません。

## 直し方: ベース文字色をターミナル緑にする

対応はシンプルで、コードブロックのベース文字色を CSS 側で暗背景向けに上書きしました。

```scss
.prose pre code {
  color: #6be38a; // ターミナル風の緑
}
```

これだけで、

- 言語なしブロックは `color: inherit` でこの緑を継承して読める
- 言語ありブロックは shiki がインラインで `style="color: ..."` を当てるので、緑は上書きされてテーマ通りの配色になる

という二つの状態が同時に成立します。テーマを潰さずに「色が付かなかったときのフォールバック」だけを差し替えられる、というのが気持ちのいい点でした。

色を決めるとき、最初は本文と同じインク色にしようかとも考えたのですが、コードブロックの暗背景はあえて "端末っぽさ" を出したい場所だったので、緑にしました。記事の文脈 (技術手順を読む場所) と色の意味 (ターミナル) が揃うほうが、読み手の頭が切り替わりやすいという判断です。

## つまずきポイント: 「テーマが効いていない」と誤読しやすい

今回いちばん時間を取られたのは、現象を見たときに最初「shiki のテーマ設定が間違っているのでは」と疑ったことでした。`dark-plus` の色定義を覗いたり、ハイライト用プラグインの初期化順を追ったりして遠回りしました。

実際には、テーマは正しく適用されていて、

- **言語ありブロック**: shiki がトークンに色を付けている → 見える
- **言語なしブロック**: shiki はノータッチ → 外側の CSS 次第

という、ライブラリの責任範囲の問題でした。検証用に隔離したページで「同じテーマでもブロックによって色付与の有無が違う」と並べて見られたのが、切り分けの決め手になりました。**ライブラリが何をしないかを把握する**のは、何をするかを把握するのと同じくらい大事だと改めて感じます。

## まとめ

- shiki は言語が指定されていないコードブロックには色を付けない (= 外側の CSS がそのまま効く)
- 暗背景の prose では `pre code` のベース文字色を明るい色に固定しておくと、言語あり/なしの両方を一度に救える
- 「テーマが壊れた?」と思ったら、まずライブラリの責任範囲を疑う
