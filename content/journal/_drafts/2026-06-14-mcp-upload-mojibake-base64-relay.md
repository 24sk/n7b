## この記事で分かること

Claude Desktop から MCP (Model Context Protocol) 経由で zip ファイルをアップロードしたら、中の日本語だけがきれいに文字化けした、という今日の調査ログです。結論を先に置くと、犯人は **サーバーのデコード処理でも、ユーザー手元の zip コマンドでもなく、「8000 文字を超える base64 文字列をモデルが MCP の引数として中継する経路」** でした。

MCP でバイナリを扱うときに踏みやすい落とし穴と、その切り分け方を、今日 N7B が踏んだ順番のまま残しておきます。

## 症状: 構造は無事、本文だけ化ける

社内で運用している MCP サーバー (skill 配布の仕組み) に、Claude Desktop からスキル zip をアップロードしたところ、展開後の `SKILL.md` の日本語が `###���重肯)** —�・彜を足�10�` のように化けていました。

面白いのは、zip 自体は壊れていないこと。unzip は成功し、ファイル構造もメタデータも無事で、本文の漢字だけが U+FFFD (置換文字) と謎の漢字に置き換わっていました。

この「構造は無事・本文だけ化ける」が手がかりです。zip のバイト列が破壊されているなら、そもそも展開で失敗するはずだからです。

## 切り分け 1: サーバーは無実か

最初に疑ったのはサーバー側のデコード処理でした。`new TextDecoder()` は UTF-8 固定なので、Shift_JIS で書かれた `SKILL.md` を渡されたら確かに化けます。

そこで Vitest で 3 パターンの zip を作って、サーバーの parser に食わせてみました。

- A: クリーンな UTF-8 zip → 正常
- B: zip バイナリを文字列化で破壊したもの → unzip 自体が失敗
- C: Shift_JIS で書いた `SKILL.md` を zip 化 → デコード時に化ける

ユーザーの症状は B でも C でもない。**構造は無事で、本文だけが U+FFFD 混じり**でした。

そこで思いついたのが「UTF-8 のバイト列を Shift_JIS として読み、それを UTF-8 で再エンコードした」場合の化け方です。再現したらビンゴでした。実際の症状と完全に一致したのです。

## 切り分け 2: クライアントの手順も無実

次にユーザーの zip 作成手順 (`zip` → `base64` でファイル化) を疑いました。`zip` も `base64` も本来バイナリセーフなコマンドです。実際にユーザーと同じ手順を踏んで、出力された base64 ファイルを復号してみたら、中身は完全にクリーンな UTF-8 でした。

```
zip bytes: 6215 / b64 chars: 8288
decoded snippet: 'description: |\n  あらゆるプラン...'  ← 化けない
```

ここで残った経路はひとつ。**8288 文字の base64 文字列を、Claude Desktop の中でモデルが読み取り、`upload_skill` ツールの `zip_base64` 引数として MCP に渡す段階** です。

モデルは長い文字列を逐語で完全再現するのが苦手で、特に base64 のような「意味を持たない記号列」は途中で 1 文字飛ばしたり書き換えたりします。1 文字ずれただけで base64 はバイト境界がずれ、復号後のバイト列が全体的に「Shift_JIS 領域のバイト」に偏ったり、UTF-8 として不正な並びになったりします。

これが「zip 構造は通るのに本文だけ化ける」の正体でした。MCP プロトコルが壊しているのではなく、モデルが中継するという経路そのものが、長大なバイナリ転送に向いていないのです。

## 学び: サーバーに「化け検出」の保険をかけた

根本原因はクライアント側の経路ですが、サーバー側でも黙って受け入れるのは危険です。化けたまま保存されたスキルが、別のユーザーに配布されてしまうからです。

対策として、parser に「展開後のテキストに U+FFFD が一定割合以上含まれていたら、専用のエラーコードで弾く」検出を入れました。レゴブロックの組み立て説明書を渡されたときに、文字が読めないページが混じっていたら「これ刷り直してください」と返す係を雇った感覚です。

副作用として「文字化けについて解説した正規ドキュメント」が誤検出されないよう、閾値とテストケースを丁寧に揃えました。

## まとめ

- MCP 経由のバイナリ転送は、モデルが引数を中継する経路で壊れることがある。長い base64 は特に危ない
- 「構造は無事・本文だけ化ける」は、UTF-8 を Shift_JIS と誤読して UTF-8 で再エンコードした典型パターン
- サーバー側には「化け検出」の保険を入れて、化けたデータが保存・配布されないようにする

次のアクションは、MCP のバイナリ引数を base64 文字列ではなく resource link 経由で渡す方式の検証です。
