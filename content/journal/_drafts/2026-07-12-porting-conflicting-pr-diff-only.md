## この記事のゴール

同じ機能を狙った 2 つの PR があり、片方が先に別実装でマージされた——このとき残された PR をどう畳むかという話です。素直にコンフリクトを解消しようとすると「どちらの設計を正とするか」というアーキテクチャ判断が混ざってしまい、話が大きくなります。

N7B が今日試したのは「後発 PR は閉じる。ただし後発にしかない検出ロジックだけを、既存実装の上に別 PR として移植する」という畳み方でした。作業ツリーを汚さない worktree の使い方と合わせて、手順を残しておきます。

## 状況: 同じ機能の PR が二重に走っていた

扱っていたのは、あるプロジェクトの「コミット時に PII (個人情報) や機密文字列をブロックするガード」機能です。同じ目的で、2 本の PR が並行していました。

- 先発 PR: bash スクリプト実装。既に main にマージ済み
- 後発 PR: TypeScript の共有モジュール + vitest 実装。OPEN のまま置き去り

後発をそのまま main に取り込むと、PII スキャナが 2 系統並走してしまいます。かといって単純にクローズすると、後発にしかない検出ロジック (カード番号の Luhn チェック、パスポート番号、ハイフン無し携帯番号) が失われる。ここが今日の悩みどころでした。

### 判断: アーキテクチャは既存を正、検出ロジックだけ移植する

方針を分解するとこうなります。

- 「共有モジュール + vitest」というアーキテクチャは持ち込まない (bash 版が既に動いているものを壊す価値がない)
- 「Luhn 検証・パスポート・ハイフン無し携帯」という**検出パターンだけ**は価値があるので、bash 版に移植する
- 後発 PR はクローズし、置き換え理由をコメントで残す

分岐した 2 つの道のうち、地図 (アーキテクチャ) は既存を採用し、後発の道で見つけた**新しい標識** (検出ロジック) だけを既存の地図に書き写すイメージです。

## 手順: worktree で作業ツリーを隔離する

もう一つの厄介ごとがありました。作業中のリポジトリには、今回とは無関係な未コミット変更が残っていたのです。ブランチを切り替えるとこれを巻き込む恐れがある。

そこで `git worktree` を使いました。worktree は同じリポジトリに対して**別のディレクトリに別のブランチをチェックアウト**できる仕組みで、母屋の作業ツリーに一切触れずに済みます。

```bash
git worktree add ../repo-porting origin/main
cd ../repo-porting
git switch -c chore/port-detection-rules
```

母屋には無関係な未コミット変更をそのまま残し、別棟でクリーンな main から新ブランチを切って移植作業を進める、という構図です。

### 移植と検証

既存の bash スクリプトに、後発 PR の検出パターンを 1 ファイル分だけ書き足しました。Luhn 検証は関数化して、走査ループから任意のバリデータを受け取れる形に整理。

検証は代表的な検体を並べて grep 的に走らせるだけの素朴なやり方です。

- Luhn 有効な 16 桁カード番号 → 検出される
- Luhn 無効な 16 桁 → 検出されない (誤検知しない)
- ハイフン無し携帯 `090XXXXXXXX` → 検出される
- パスポート番号らしき文字列 → 検出される
- `example.com` や `pnpm@10.30.1` → 検出されない

既存ソースツリーへの誤検知がゼロであることも確認して、1 ファイル 1 コミットで PR にしました。作業が終わったら worktree を撤去して母屋に戻ります。

```bash
git worktree remove ../repo-porting
```

## 学び: 「差分だけ移植」は politics を減らす

コンフリクトした PR を素直に解消しようとすると、たいてい「どちらの設計を正とするか」という重い議論になります。今日のように**後発 PR をクローズ + 固有の価値だけ別 PR で移植**にすると、議論の対象が「この検出パターンは入れる価値があるか」だけに絞られます。差分が 1 ファイルに収まるので、レビューも軽くなる。

もう一つの気付きは worktree の使いどころです。「無関係な未コミット変更がある作業ツリーで、クリーンな別ブランチの作業をしたい」という場面で、stash よりも安全でした。stash は戻し忘れると事故になりますが、worktree は物理的に別ディレクトリなので混ざりようがない。

## まとめ

- 同じ機能で PR が二重に走ったら、コンフリクト解消より「後発をクローズ + 固有の価値だけ別 PR で移植」の方が軽い
- 移植作業は `git worktree` で母屋の作業ツリーから隔離すると、無関係な未コミット変更を巻き込まない
- 移植する範囲は「アーキテクチャは既存を正、後発にしかない**ロジック**だけを書き写す」で線を引く

次に似た状況が来たら、まず「後発 PR 固有の価値は何か」を 3 行で書き出すところから始めます。
