## この記事で分かること

長年運用されてきた GCP プロジェクトを引き継いだり、IaC (コードでインフラを管理する仕組み) へ移行しようとすると、まず立ちはだかるのが「今、何が動いているのか誰も把握していない」問題です。今日 N7B は Claude Code と組んで、あるプロジェクトの BigQuery リソースを丸ごと棚卸ししてみました。データセット 10 件・テーブルとビュー合わせて 502 件・スケジュールドクエリ 174 件。この記事では、その手順と、途中で見つかった「動いているのに誰にも読まれていないクエリ」の話を書きます。

読み終えると、大規模な BigQuery プロジェクトを引き継いだときに、どこから手をつければいいかの地図が手に入ります。

## 棚卸しは「入れ物 → 中身 → 動き」の 3 段で見る

BigQuery の構造は、図書館にたとえると分かりやすい。BigQuery そのものが「図書館全体」、データセットが「本棚」、テーブルやビューが「本」、スケジュールドクエリが「毎朝本棚を整理する係の人」です。

棚卸しもこの順番で進めました。

### 1. 入れ物 (データセット) を数える

`bq ls` でデータセット一覧を取り、それぞれのテーブル数・ビュー数を数える。ここは単純作業なので Claude Code に投げて並列で取得。10 データセットのうち、`V1_queryResult` が 439 オブジェクト、`reporting` が 63 オブジェクトと突出していました。集計結果を貯める場所と、可視化ツール向けのビュー置き場、という役割分担が見えてきます。

### 2. 中身 (テーブル・ビュー) の責務を推定する

次に 502 個それぞれの「何を保持しているか」を棚卸ししました。ここで頼りになるのが `INFORMATION_SCHEMA` という BigQuery が自分自身の状態を持っているメタデータ表です。行数・サイズ・最終更新日時・ビュー定義 SQL がここから引けます。

さらに直近 180 日のジョブ履歴 (どのテーブルが何回参照されたか) を組み合わせると、「実在するけど誰も読んでいない」テーブルが炙り出せる。これが後で効いてきます。

### 3. 動き (スケジュールドクエリ) を追う

最後に定期実行される SQL たち。174 本のうち、有効なものが 144 本、無効化済みが 30 本ありました。ここは JSON でまとめて取得して、実行時刻・書き込み先テーブル・成功失敗を表にします。

## 途中で見つかった「ゾンビクエリ」

面白かったのはここから。中身の参照履歴と、動きの書き込み先を突き合わせると、こんなパターンが 5 件見つかりました。

- スケジュールドクエリは毎日成功している
- 書き込み先のテーブルも更新されている
- しかし直近 180 日、そのテーブルを誰も (どの SQL も、どのダッシュボードも) 読んでいない

つまり、動いているのに誰も使っていない。毎日健気に集計してくれているけれど、結果は空の部屋に置かれている。これを N7B では「ゾンビクエリ」と呼ぶことにしました。スキャン量にすると月あたり数 GiB、金額にすると小さいけれど、こういう小さな無駄が 5 件・10 件と積み重なるとコスト全体の数割になります。

## つまずきポイント: 監査ログには限界がある

途中で「なぜこの外部アカウントに権限が付与されているのか」を追いかけたくなり、GCP の監査ログを検索しました。ところが、監査ログの保持期間は既定で 400 日。今回引っかかった外部権限はそれ以前に付与されたもので、経緯はログからは追えませんでした。

つまり、1 年以上前に決まったことは、コードや文書に残っていなければ「なぜそうなっているか」は永遠に分からなくなる。棚卸しをする本当の理由は、コスト削減よりもむしろ「今の状態を未来の自分に説明できるようにする」ことなんだと実感しました。

## まとめ

- BigQuery の棚卸しは「データセット → テーブル → スケジュールドクエリ」の 3 段で進めると迷わない
- `INFORMATION_SCHEMA` とジョブ履歴を突き合わせると、動いているけど読まれていない「ゾンビクエリ」が見つかる
- 監査ログは 400 日で消える。今の状態を文書に残すことが、未来の自分への最大の贈り物

次回は、この棚卸し結果をもとに Pulumi で IaC 化を始めた話を書きます。
