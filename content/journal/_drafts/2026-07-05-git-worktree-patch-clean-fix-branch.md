## この記事で分かること

メインの作業ツリーに「別の機能ブランチ上で編集した、無関係な小さな修正」が未コミットで残ってしまう ── そんな状態から、main ベースのきれいな `fix/` ブランチを作って PR に出すまでの手順をまとめます。今日 N7B が Claude Code と一緒にハマって、`git worktree` と `git apply` の組み合わせで抜け出した実体験のログです。

結論を先に言うと、**別 worktree に main 相当の作業場所を用意し、そこにパッチだけを移植する**のが一番安全でした。

## 起きていた状況

記事一覧のタグフィルタに `:focus-visible` のアウトラインを足す、というアクセシビリティの小さな修正がありました。ところが変更を書いた場所が悪かった。

- メイン作業ツリー `~/dev/skedachi` は `feat/article-heading-copy-link` という**別の機能ブランチ**にチェックアウト中
- その状態で `app/pages/articles/index.vue` を編集し、未コミットのまま放置
- ここから `fix/` ブランチを切ると、機能ブランチの先行コミットまで PR に混入する

例えるなら、料理中の鍋 (機能ブランチ) の隣で別の一品 (fix) を作り始めてしまい、混ぜずに皿へ移したい状態です。

## 解決の流れ

幸いこのプロジェクトでは `git worktree` で別ディレクトリに main 相当のチェックアウトを用意していました。ここを「きれいなまな板」として使います。

### 1. パッチが当たるか先に確認する

まず、機能ブランチが対象ファイルを編集していないか (＝ main と内容が同じか) を見ます。

```bash
git diff main -- app/pages/articles/index.vue
```

差分が空なら、未コミット変更は main ベースにもクリーンに当たると判断できます。ここを飛ばして先に進むと、後でコンフリクトの海に沈むので必須の一手です。

### 2. 未コミット差分をパッチにして取り出す

メイン作業ツリー側で:

```bash
git diff -- app/pages/articles/index.vue > /tmp/tag-filter.patch
```

差分をファイルとして書き出しておくと、この後 worktree 側で使い回せます。

### 3. worktree 側で fix ブランチを切ってパッチ適用

main ベースの worktree に移動して:

```bash
git switch -c fix/article-tag-filter-a11y
git apply /tmp/tag-filter.patch
git diff  # 元の diff と一致するか確認
```

適用後の diff が元と 1 行も違わないことを確認してからコミット。これで機能ブランチのコミットは 1 つも混じらない、修正だけの PR が作れます。

### 4. メイン作業ツリーの残骸を捨てる

最後に、メイン側に残った同じ差分を破棄します。

```bash
git checkout -- app/pages/articles/index.vue
```

破棄前に「PR にコミット済みの内容と行単位で一致しているか」をもう一度見比べておくと、取り返しのつかない事故を防げます。

## つまずきポイント

一番危なかったのは **「機能ブランチ上で fix ブランチを切りたくなる誘惑」** でした。`git switch -c` はどのブランチからでも派生できてしまうので、深く考えずに切ると先行コミットが全部乗ってきます。PR の diff を開いた瞬間に「なぜ 20 ファイル変わっているのか」と気付く、あのパターンです。

もう一つは worktree 側の `node_modules` が空だったこと。lint を走らせようとしたら止まったので `pnpm install` からやり直しました。worktree は Git のメタデータしか共有しないため、依存は別物と割り切っておくのが安全です。

## まとめ

- 別ブランチ上の未コミット差分は、**パッチ化 → main ベースの worktree に適用**で切り離せる
- パッチを当てる前に「対象ファイルが両ブランチで同一か」を必ず確認する
- worktree は依存関係を共有しないので、`node_modules` は都度用意する

次に似た状況に遭遇したら、慌てずに `git worktree list` から見直す。
