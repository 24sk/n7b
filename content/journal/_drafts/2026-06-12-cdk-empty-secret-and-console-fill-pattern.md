## 結論: CDK は「器」だけ作り、中身はコンソールで入れる

今日 N7B がインフラ側の作業で踏んだのは、**RDS の接続情報を Secrets Manager にどう持たせるか**という小さいけれど誤解の多いテーマでした。結論はシンプルで、CDK では空の Secret(器)だけを作り、ホスト名やパスワードなどの実値は AWS マネジメントコンソール(Web 管理画面)から人が手で入れます。

この記事を読むと、次の 2 点が分かります。

- なぜ CDK のコードに接続情報を書かず、わざわざ「空の器」を作るのか
- 「コンソールに投入」という言葉で取り違えやすい落とし穴(GitHub Secrets と混同するパターン)

対象は、AWS CDK で RDS や外部 DB を扱い始めた Web / インフラ開発者です。

## やったこと: 2 本の Secret を CDK で追加した

別環境にある既存 DB 2 本(仮に `cs-db/stg` と `cs-admin-db/stg` と呼びます)から、統合先の DB へデータを import する仕組みを組んでいます。import を走らせる GitHub Actions のランナーは VPC の外にいるので、ソース DB の場所も認証情報も最初は何も知りません。そこを埋めるのが Secrets Manager の役目です。

CDK 側でやったのは、既存の Secret 生成パターンをそのままコピーして 2 本足すだけ。3 本とも構造が同じだったので、`createDbSecret` というヘルパー関数に集約しました。`cdk diff` で既存 Secret に差分が出ないことを確認してからデプロイ、Secret 2 本が AWS 上に作られたところまでが今日の前半です。

ポイントは、この時点で **Secret の中身はまだ空** ということです。host も username も password も入っていません。

## なぜ空の器なのか: コードに秘密を書かない設計

ここがこのパターンの肝です。

もし CDK のコードに `password: "hogehoge"` と直書きしてしまうと、Git リポジトリに本物のパスワードが残り、合成された CloudFormation テンプレートにも平文で書かれ、デプロイログにも痕跡が残ります。これは事故のもとです。

だから CDK では「器」だけ宣言する、という分業をします。たとえるなら、引っ越し業者が空のダンボール箱だけを部屋に並べていく作業に近いです。中に入れる貴重品は本人がコンソールから直接入れる。コードレビューも CI ログも、ダンボールの形と置き場所しか見ない構造になります。

実値の入れ先は AWS マネジメントコンソールの Secrets Manager 画面、もしくは AWS CLI の `update-secret` です。手作業ではあるものの、環境ごとに 1 回入れれば終わりで、頻度が低いので運用上は許容範囲に収まります。

## つまずきポイント: 「コンソール」を GitHub と取り違える

今日いちばん面白かったのは、タスクの読み手側で起きた誤解です。「コンソールに投入する」と書かれていたのを、**GitHub Secrets や GitHub Actions の環境変数に入れる作業**と読み違えるパターンが発生しました。

これはかなり起きやすい誤読です。理由は 3 つあります。

- 「コンソール」という単語は GitHub にも AWS にも、シェルにもある
- import を走らせる主体が GitHub Actions なので、文脈的に GitHub 側の話に見える
- CDK で「Secret を作った」と聞くと、もう中身まで入っていそうに錯覚する

対策として N7B では、タスクの文章で「AWS マネジメントコンソール(Web 管理画面)」と毎回フルネームで書くようにしました。半行の補足を入れるだけで、後から読む人(数ヶ月後の自分を含む)の事故率がぐっと下がります。

もう 1 つの学びは、Secret の状態確認は値そのものを表示せず「キーごとに空かどうかだけ」を見るスクリプトで済ませるという作法です。今日も Claude Code に確認させた際、値は伏せたままで `cs-integrated-db/stg` だけが投入済み、残り 2 本は port 以外空、という結果だけが返ってきました。確認ログにも秘密が残らないので、この型は他の Secret 運用にも流用できそうです。

## まとめ

- CDK では Secret の「器」だけ作り、中身はコンソール(AWS Web 画面)で人が入れる二段構えにする
- 「コンソールに投入」は GitHub ではなく AWS 側の話だと、文書側で明示しておくと事故が減る
- Secret の状態確認は値を出さず、キーごとの空 / 投入済みだけを見るスクリプトに留める

次のアクションは、この空 Secret パターンを RDS 以外の外部 API キー管理にも広げて、運用ドキュメントを 1 枚にまとめることです。
