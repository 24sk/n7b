## この記事で分かること

溜まった Dependabot の PR (パッケージ更新の自動 PR) を Claude Code にまとめて処理させたら、どこまで自動化できて、どこで人間が介在すべきかが見えてきた、という話です。今日 N7B があるリポジトリで実際にやってみた作業を辿りながら、次の 3 点を持ち帰れるように書きます。

- CLI エージェントに「一括マージ」を任せるときの落とし穴
- ベースブランチから遅れた PR (BEHIND 状態) の扱い方
- 人間が最後まで持つべき判断は何か

## きっかけは「PR 一覧の掃除」

あるスクレイピング系のリポジトリで、Dependabot が出した PR が数件溜まっていました。`body-parser` のパッチ、`brace-expansion` のマイナー、`prettier` のマイナーなど、いわゆる「軽微な依存関係更新」ばかりです。

そこで Claude Code にこう頼みました。「軽微な依存関係の PR は全てマージしてください。不要な PR はクローズしてください」。

面白かったのは、エージェントが最初に「一括ループ」でマージを試みて、途中でブロックされたことです。GitHub API 側にレート制限やバッチ処理の制約があり、`for` で回すような操作は途中で止められる。エージェントはそこで方針を切り替え、1 件ずつ順番に処理するモードに落として最後まで完走しました。

### 具体的に何が起きたか

結果はシンプルです。

- パッチ更新 2 件 → そのままマージ
- マイナー更新 1 件 → ベースブランチより遅れていた (BEHIND) ため、ブランチを更新してから自動マージを予約

この「BEHIND」というのは、PR のブランチが main の最新に追いついていない状態のことです。レゴで例えると、土台のブロック (main) が積み増しされたのに、上に載せる新しいブロック (PR ブランチ) が古い土台の形で作られたまま、という状態です。そのままだと乗らないので、一度土台に合わせて作り直す (rebase または merge) 必要があります。

エージェントはこれを検知して、ブランチ更新 → CI 待ち → auto-merge 予約、という順序を自分で組み立てました。人間が「BEHIND だから更新して」と指示しなくても、状態を読んで動く。ここは想像より賢く動いた部分です。

## つまずいたのは「クローズ理由コメント」

一方でハマったのが、不要 PR をクローズするときの挙動です。最初エージェントは「クローズ理由をコメントに添えてから閉じる」動きを試みたのですが、権限か API の仕様でブロックされました。結局コメントなしでクローズする方針に切り替えて処理を完了しています。

ここで学びが 1 つ。**エージェントの「丁寧さ」がツール側の制約と衝突することがある**。人間なら「理由を書いてから閉じたい」と思うのは自然ですが、Bot アカウントや App の権限セット次第でその一手が通らない。運用ルールとして「クローズ理由は PR 本文に事前に書いておく」「コメントは別途手動で残す」など、エージェントが完結できる形に設計を寄せた方が摩擦が減ります。

もう 1 つの学びは、**「軽微」の判定は結局人間が握る**という点です。パッチ更新は基本安全、マイナーは要確認、メジャーは必ずレビュー、という粒度感を明示しないと、エージェントは全部同じ扱いにしてしまう危険がある。今回は事前にリポジトリの運用ルールが整っていたので事故はありませんでしたが、指示文だけで動かすなら「パッチのみ auto-merge、それ以外は列挙して報告」くらいまで絞る方が安心です。

## まとめ

- Dependabot PR の一括処理は Claude Code に任せられるが、API 制約で「1 件ずつ」に自然と落ちる
- BEHIND 状態のブランチ更新まで含めて自律的に組み立てられたのは収穫
- 「軽微」の定義とクローズ運用は人間側で先に決めておくと摩擦が減る

次は、この流れを毎週決まった曜日に走らせる「Dependabot 掃除デー」のワークフロー化を試します。
