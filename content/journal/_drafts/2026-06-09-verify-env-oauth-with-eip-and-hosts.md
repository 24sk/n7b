## この記事のゴール

検証用にもう 1 台だけ EC2 を立てて、本番や既存ステージングと「並べて比べる」ことはよくあります。今回 N7B が直面したのは、その比較用 EC2 で **Google OAuth 認証後の画面まで触りたい** という要望でした。普通に考えると専用ドメインを切り、ACM で証明書を発行し、Google OAuth クライアントにコールバック URL を追加して……と工程が膨らみます。

それを **EIP(固定 IP) と手元の hosts ファイル書き換えだけ** で済ませた話を書きます。読み終わると、検証 EC2 を 1 台増やしたいときに「ドメインを切らずに認証付き画面を触る」最短ルートが手に入ります。

## 出発点: SG を開けただけでは画面は出ない

最初の要望は「SSM 経由だけでなく HTTPS でも検証 EC2 にアクセスしたい」でした。CDK 側で app SG の 443 を `0.0.0.0/0` に開ける変更を入れて `cdk deploy`。これで終わり……と思いきや、実機を確認すると `PublicIp = null`。SG を開けてもパブリック IP が無ければインターネットからは届きません。

ここで EIP(Elastic IP、AWS が払い出してくれる固定のグローバル IP) を割り当てて関連付けます。EIP のうれしいところは、**インスタンスを stop/start しても IP が変わらない** こと。検証環境は週次で自動停止・起動するスケジュールが組まれているので、毎週 URL が変わるのは避けたい。EIP ならそこを固定できます。

```
Allocation ID: eipalloc-xxxx
EIP:           13.159.247.11
```

割り当て後、`https://13.159.247.11/` で叩くと HTTP/2 200。タイトルは `<title>CS_ADMIN</title>`。画面までは出るようになりました。

## 認証ゲートにぶつかる

次の壁は Google OAuth です。保護パス `/users` を叩くと 302 でログイン画面に戻され、`/oauth/google` を叩くと `accounts.google.com` にリダイレクトされます。つまり SG が全公開でも、アプリ側のログインで止まる設計。安心材料ではあるのですが、**ログインを完了させない限り中身は触れない**。

ここで `/oauth/google` の `redirect_uri` を覗くと、コールバック先は既存ステージングのドメイン (`https://cs-admin.stg.example.com/oauth/google_callback`) に固定されていました。Google OAuth クライアントには、このコールバック URI が既に登録されています。

素直に行くなら、比較 EC2 用に新しいドメインを切り、ACM で証明書を発行し、Google OAuth クライアントに新コールバック URI を追加……となります。検証目的のためにそこまで触りたくない。

## hosts ファイルで「同じドメイン」に化けさせる

打開策は身も蓋もなく、**手元の PC の `/etc/hosts` を書き換えて、既存ステージングのドメインを比較 EC2 の EIP に向ける** ことです。

```
13.159.247.11  cs-admin.stg.example.com
```

たとえるなら、宛先ラベルだけ貼り替えて同じ住所の別の家に荷物を届けるようなもの。アプリから見ると Host ヘッダは見慣れたドメインのまま、実体は比較 EC2。事前に `curl -H 'Host: cs-admin.stg.example.com' https://13.159.247.11/` で叩いて、Host ヘッダ付きでもちゃんと 200 が返ることは確認済みでした。

コールバック URI も既存ステージングと同じ文字列なので、Google 側の設定は 1 文字も触らずに済みます。

## つまずきポイント: 自己署名と HSTS

比較 EC2 の nginx は自己署名証明書なので、ブラウザでアクセスすると当然ながら警告が出ます。ここで効いてくるのが **HSTS(HTTP Strict Transport Security、ブラウザに「次回からは絶対 HTTPS で来い」と覚えさせる仕組み)** の有無。HSTS が有効なドメインだと、自己署名警告のページから「無視して進む」ボタンが消えて、貫通できないことがあります。

今回は既存ステージングも比較 EC2 も `Strict-Transport-Security` ヘッダを返していませんでした。これは事前に `curl -I` でレスポンスヘッダを覗いて確認しています。HSTS が無いので、自己署名警告は手動で承認して通過可能。もし HSTS が有効だったら、この手は使えず素直にドメインを切る判断になっていました。

## まとめ

- 検証 EC2 を 1 台だけ追加で公開したいなら、**SG の 443 開放 + EIP + hosts 書き換え** の三点セットでドメインも証明書も追加せず済む
- OAuth コールバック URI が既存環境と同じ文字列なら、hosts でホスト名を化けさせるだけで認証フローが完結する
- 同じ手は **HSTS が無効** という前提でだけ成立する。事前に `curl -I` でヘッダを確認しておく

次は、この比較 EC2 を週次 stop/start に組み込んでも EIP が外れないか、運用しながら見届けます。
