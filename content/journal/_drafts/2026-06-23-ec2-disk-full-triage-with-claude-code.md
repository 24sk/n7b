## この記事のゴール

本番 EC2 のディスク使用率が 100% に達し、スクレイピング処理が次々と失敗していた日のログを残します。読んで分かるのは「CPU・メモリではなくディスクが詰まっているとき、Claude Code と CloudWatch メトリクスをどう組み合わせて原因の住所まで降りていくか」という一連の段取りです。インフラのアラートが鳴ったときに、まずどこを見て、どう削るかの地図として使えます。

結論を先に言うと、原因は 3 つの層に分かれていました。アプリが吐き続ける CSV、SSM Run Command の残骸、systemd journal。順に剥がしていったら 30GB のうち 22GB が使用、空き 9GB という状態から、空き 23GB(使用率 26%) まで戻りました。

## まず CPU を疑い、外す

アラートの第一印象は「スクレイピングが詰まっているから CPU かメモリだろう」でした。ところが CloudWatch を 14 日分眺めると、t3.medium の CPU クレジットは常に上限の 576 で張り付き、平均使用率は 4%。バースト型インスタンス特有の「クレジット枯渇でスロットル」も起きていない。メモリも平均 17.5%、ピーク 56%。

ここで「CPU は犯人ではない」と確定させたのが大きくて、容疑者リストから 2 つ消えると、視線が自然にディスクへ向きます。Claude Code に CWAgent のディスクメトリクスを取らせると、6/11 まで 64〜70% で平らだったグラフが、6/12 から毎日 +2〜2.5% で直線的に増え、6/22 に 100% に到達していました。

ノコギリ型(溜まっては掃かれる) ではなく単調増加。これは「何かが書き込まれっぱなしで誰も消していない」というリーク型のパターンです。家計簿で言えば、固定費が増えたのではなく、毎日少しずつ引き落とされ続けている口座を見つけた感覚に近い。

## 実機に降りて住所を特定する

メトリクスで「ディスクが犯人」までは分かっても、どのディレクトリかまでは見えません。SSM 経由で読み取り専用のシェルを開き、`du` で大きい順に並べました。

出てきた内訳がこちら。

```
30G  /
├─ 16G  /var
│   ├─ 12G  /var/lib/amazon/ssm/.../document
│   ├─ 2.9G /var/log/journal
│   └─ 674M /var/lib/mysql
└─ 11G  /data (アプリの CSV 出力先)
```

面白かったのは、最初「ログが溜まっているのだろう」と決めつけていたら、純粋なログ (journal) は 2.9GB しかなく、最大の容量食いは SSM Run Command の実行履歴 12GB と、アプリが書き出した CSV 11GB だったことです。知識の呪いというか、「ディスク逼迫 = ログローテ不備」という先入観が一度ハズレた。

## 安全度順に剥がす

削除は「当日稼働中のデータには触らない」を最優先にしました。具体的には、

- CSV は当日 (JST 6/23) 分だけ保持し、それ以前を削除
- SSM の orchestration 残骸は 24 時間より古いものだけ削除 (稼働中コマンドを巻き込まない)
- journal は `journalctl --vacuum-size` で上限を切る

ドライランで「909 ファイル / 約 9GB」と件数とサイズを先に確定させてから本実行、というのを Claude Code との会話で挟んでいて、これが本番作業の精神衛生に効きました。`rm -rf` をいきなり打つのではなく、`find ... -print` で対象を一度全部見る、というワンクッションです。

結果は、22GB 使用 → 7.8GB 使用、空き 23GB。スクレイピングの CSV 書き込み失敗もそのまま解消しました。

## つまずきと学び

一番の学びは「ディスク逼迫の正体は意外と複合的」ということです。今回も犯人は 1 人ではなく、アプリ・OS・運用ツールの 3 層から少しずつ漏れていた。1 つだけ削っても根治しないし、逆に 1 つ削れば残り 2 つに気付きやすくなる。

もう 1 つは、SSM 経由のシェルが「設定ファイル編集とサービス再起動」でブロックされたこと。削除はできるが恒久対策の設定変更は別承認、という線引きが効いていて、本番作業の権限分離としては正しい挙動でした。代わりに journal の保持上限設定や、cs_auto 側で CSV を出力後に消す改修が、次の宿題として残っています。

## まとめ

- CPU・メモリのメトリクスを先に見て「犯人ではない」と確定させると、視線がディスクに集中できる
- ディスク逼迫はアプリ出力・運用ツール残骸・OS ログの 3 層を疑う。「ログが原因」と決めつけない
- 本番削除はドライランで件数とサイズを確定させてから実行する。当日分は触らない

次のアクションは、CSV の自動掃除 cron と journal 保持上限の恒久化。手で消す運用は 1〜2 週間でまた同じ状態に戻ります。
