## 平日の朝にコストレポートが届く仕組み

2026-05-26 の朝、Claude Code が黙々と AWS のコストレポートを吐き出していました。stg 環境のレポートを生成し、続けて prod のレポートを生成し、最後に両方を突き合わせた横断サマリを作る。N7B のエンジニアは寝ているか、すでに別の作業に入っているかで、誰もキーボードを触っていない。

これは Claude Code の `scheduled-tasks` を使った定期実行の話です。今日はその構成と、運用してみて見えてきた勘どころを書き残しておきます。

## scheduled-tasks の基本構造

Claude Code には `.claude/scheduled-tasks/<task-name>/SKILL.md` という形でタスクを定義する仕組みがあります。今回 N7B で動かしているのは `cost-report-daily-weekday` という名前のタスクで、平日の決まった時刻に AWS のコストを取得してレポート化するもの。

SKILL.md の中身は、おおまかに次のような構成になっています。

- タスクの目的 (何を生成するか)
- 対象環境のリスト (今回は stg と prod)
- 出力先のパス規約
- 失敗時の挙動 (リトライするか、ログだけ残すか)

実行されるとき、Claude Code は「これは自動実行であり、人間は不在」という前提のコンテキストを受け取ります。プロンプトの冒頭に明示されていて、判断が必要な箇所は質問せずに合理的な選択をして、選んだ根拠を出力に残すルール。これが地味に効きます。

## 「人間が不在」を前提にする設計

対話的に Claude Code を使っていると、迷ったときに聞き返してくる挙動はむしろ歓迎されます。けれどスケジュール実行ではこれが致命傷になる。聞かれても答える人がいないので、タスクがそこで止まる。

だから SKILL.md には「曖昧なケースでどう振る舞ってほしいか」を先回りして書き込んでおきます。たとえば「コスト取得 API が一部リージョンで失敗したら、その旨をレポートに明記して残りのリージョンで続行する」といったルール。エラーを握りつぶさず、かといって全停止もしない、その中間の振る舞いを定義しておく。

## stg → prod → 横断サマリ の順序

今回のタスクは 3 段構成です。

1. stg のコストレポート生成
2. prod のコストレポート生成
3. 両環境を突き合わせた横断サマリ

順序を明示しているのは、横断サマリが前段 2 つの成果物に依存するから。Claude Code は自律的に判断するとはいえ、依存関係は SKILL.md にフローとして書いておいたほうが安定します。実際に今朝のログを見ると、stg を終えてから prod に進み、最後にサマリを生成するという順序が崩れずに走っていました。

## 運用してみて見えてきたこと

動かし始めて気づいたのは、レポート自体よりも「毎日生成され続けている」という事実のほうが価値が大きいということ。週次で人手で棚卸ししていた頃は、急にコストが跳ねた日の検知が数日遅れることがありました。日次で残っていれば、差分を見れば異常はすぐわかる。

もう一つは、SKILL.md がそのままドキュメントになっていること。タスクの定義ファイルが運用手順書も兼ねるので、別途 Wiki に書き写す手間がない。Claude Code が読むものと、人間が読むものが同じファイルというのは、地味ですが運用負荷を下げる効きどころでした。
