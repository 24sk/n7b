## 結論: 道具は「自分の操作の中心」に寄せる

今日は OSS の tmux プラグイン `craftzdog/tmux-claude-session-manager` を読み解き、`ttmux` という名前で自分のリポジトリに丸ごと移植し、実際の tmux に導入して動かしてみました。結果として、最終的には全部ロールバックして、Mac ネイティブの `cmux` (複数の Claude Code セッションを GUI のタブとペインで束ねるアプリ) に戻しました。

この記事で渡したいのは 3 つ。プラグインの中身は何で出来ているか、導入の落とし穴はどこか、そして「移植したのに採用しない」という判断をどう下したかです。複数 Claude セッションをどう束ねるかで迷っている人向けの、実地メモです。

## 160 行の bash でできていた

元のプラグインは、驚くほど小さい構成でした。エントリポイントの `claude_session_manager.tmux` と、`scripts/` 配下の 5 本のシェルスクリプト。合計でおよそ 160 行の bash です。

中身を要約するとこうなります。

- `prefix + y` で、今いるディレクトリ専用の Claude セッションを `claude-<ハッシュ>` という名前で起動する (既にあれば再アタッチ)
- `prefix + u` で、`claude-` から始まる全セッションを fzf で一覧表示し、ジャンプ / kill できる
- Claude Code の hook (`PreToolUse` / `Stop` など) から `state.sh` を叩いて、`working` / `waiting` / `idle` を tmux のユーザーオプションに書き込む

つまり、ステート管理の正体は「tmux の `@claude_state` というオプションに 1 単語を書き込むだけ」。レゴブロックでいえば、tmux という土台に小さなブロックを 5 個だけ載せている構造で、読めばすぐ全体像が掴めます。移植もそのまま忠実に再現するだけで済みました。

## 導入してハマった 2 つの落とし穴

移植したものを自分の tmux に導入する段で、2 か所つまずきました。

### tpm を使っていない

世の中の tmux プラグイン解説はほぼ tpm (Tmux Plugin Manager) 前提で書かれています。N7B の `~/.tmux.conf` には tpm が入っていないので、tpm のインストールから始めるか、別ルートを取るか迷いました。結論は後者で、`run-shell ~/dev/ttmux/claude_session_manager.tmux` の 1 行を `.tmux.conf` に足すだけで済みました。プラグインの実体はただの shell スクリプトなので、tpm はあくまで「自動で git clone してくる便利屋」に過ぎないと再確認できた瞬間です。

### Cmd+D は tmux の分割ではない

もう 1 つは見落としがちな話。プラグインを入れて `prefix + y` を押しても画面が変化しないように見えた原因は、ターミナルアプリの `Cmd + D` で画面を上下に割っていて、そのうち下半分 (80×20) でだけ tmux が動いていたことでした。つまり tmux のクライアントサイズが、ターミナルアプリのペイン分割によって半分に削られていた。`display-popup` のような全画面系の UI を出す機能は、この「tmux が見えている範囲」の中でしか展開できません。

ここで学んだのは、「画面の分割」には 2 層あるという当たり前の事実です。ターミナルアプリ層の分割と、tmux 層の分割。両方を同時に使うと、思った場所に UI が出てこなくなります。

## なぜ最終的に cmux に戻したか

移植は綺麗にできて、動作も正しいことを検証しました。それでも採用しなかったのは、自分の操作の中心が tmux ではなかったからです。

- tmux 中心で生活している人なら、`prefix + y` で起動して `prefix + u` で巡回する流れはとても自然
- Mac ネイティブの cmux はマウスとタブ UI が中心で、複数セッションの「今どれが入力待ちか」がアイコンで見える
- N7B は普段から cmux のタブで複数プロジェクトを切り替えていて、tmux はサーバー側作業のときだけ使う

つまり同じ問題 (複数 Claude セッションをどう束ねるか) を解く道具が 2 つあって、自分の「操作の重心」がどちらに寄っているかで答えが変わる、というだけの話でした。良いプラグインだからといって自分の重心とずれた場所に道具を置くと、結局使われずに錆びていきます。

## 学び: 移植は「読むため」にやってもいい

今日いちばん良かったのは、移植というプロセスそのものが、コードを読む速度を最大化してくれたことです。READ ONLY で眺めるのと、自分のリポジトリに同じ構造を作り直すのとでは、解像度が 2 段違います。160 行の bash の意図がほぼ全部腹落ちしました。

採用しなくても、構造を理解した経験は残ります。次に似たプラグインを設計するとき、「セッション名のプレフィックスで管理対象を識別する」「状態は tmux のユーザーオプションに 1 単語で書く」というパターンを自分の引き出しから取り出せます。

## まとめ

- `craftzdog/tmux-claude-session-manager` は 160 行の bash で、セッション名プレフィックスと tmux ユーザーオプションだけで成立している小さく綺麗な設計
- 導入時の落とし穴は「tpm 前提の解説に流されないこと」と「ターミナルアプリ側の画面分割と tmux の分割を混同しないこと」
- 道具選びは機能比較ではなく「自分の操作の重心がどこにあるか」で決める。N7B は cmux に戻した
