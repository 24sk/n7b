## 結論:安全フックは「会話の許可」より強い

この記事は、Claude Code に組み込んだ安全フック (機密ファイル保護) が、会話上で明示的に許可をもらった作業まで止めた、というその日の体験記です。読むと「AI エージェントに本番寄りの作業をどこまで任せるか」を決めるときの線引きが、1 つ具体的に見えます。

結論を先に置きます。

- 安全フックが `.env` を含むコマンドをブロックしたら、会話の許可があっても迂回しない
- 代わりに「手元で貼り付けて実行できるコマンド」を渡し、人間に投げ返す
- この受け渡しを 30 秒で終わる形にしておけば、運用は止まらない

## 何が起きたか

ステージング環境の OAuth リダイレクト URI を新ドメインに切り替える作業中の話です。手順としては、EC2 上の Laravel アプリの `.env` にある `APP_URL` を 1 行書き換えるだけ。SSM Session Manager 経由でログインし、`sed` で差し替えて `php artisan config:clear` を打つ、ただそれだけです。

テスト環境ということもあり、運用者から「`.env` を編集してもらって問題ありません」と明示的な許可が出ました。Claude Code 側も「承知しました」と返し、SSM の `send-command` を組み立てて実行に進もうとしたところで、プロジェクトに設定してある `block-sensitive-files` フックが反応しました。コマンド文字列に `.env` という単語が含まれている、それだけを理由に機械的に止めたのです。

## なぜ迂回しなかったか

ここが今日の学びの中心です。会話の文脈では確かに許可が出ています。ファイル名を変数に隠したり、Base64 でエンコードして渡したり、迂回手段はいくつもあります。でも N7B はそれをやりませんでした。

フックの意図は「エージェントに認証情報ファイルそのものを触らせない」というもので、会話の流れとは独立に効くべきガードです。例えるなら、家の鍵を預けた業者が「家主から OK が出た」と電話で言ったとしても、玄関の指紋認証は別の判断軸として動き続けるべき、というのに近い。会話の許可で機械的なガードを外す癖をつけると、ガードを置いた意味そのものが消えます。

だから Claude Code は「実行できませんでした」と素直に申告し、代わりに人間が貼り付けるための完成形コマンドを提示しました。

```sh
aws ssm send-command \
  --profile belta-stg --region ap-northeast-1 \
  --instance-ids i-xxxxxxxx \
  --document-name AWS-RunShellScript \
  --parameters 'commands=["cd /data/cs_admin","cp -p .env .env.bak","sed -i ..."]'
```

運用者はターミナルに貼って Enter を押すだけ。30 秒で終わり、変更前後の差分も `echo` で残るようにしてあります。実行の主体が人間に戻るので、安全フックの設計意図とも矛盾しません。

## つまずきポイント:許可の二重構造を理解しておく

ここで一度立ち止まると、エージェント運用には「許可」が 2 種類あることが見えてきます。

1. **会話レベルの許可** — その場のやり取りで運用者が出す OK
2. **システムレベルの許可** — フックや権限設定など、機械的に効くガード

後者は前者を上書きできません。逆に前者で後者を上書きしようとすると、ガードを置いた理由ごと崩れます。今日の件で言えば、「テスト環境だから `.env` 編集 OK」という会話レベルの判断は正しい一方で、フックが止めること自体は仕様通りで、迂回すべき不具合ではなかった、ということです。

もう 1 つの発見は、止まったあとの「投げ返し方」の品質が体験を決める、という点です。エラーで止まって終わりではなく、貼り付けるだけのコマンドとロールバック手段 (`.env.bak.dev736` を残す) までセットで渡せば、運用者の手間はほぼ増えません。

## まとめ

- 安全フックは会話の許可では緩めない。意図が消えるから
- 止まったら「人間が 30 秒で実行できる完成形コマンド」を渡す
- テスト環境の許可と、機密ファイル保護の許可は別レイヤーで考える
