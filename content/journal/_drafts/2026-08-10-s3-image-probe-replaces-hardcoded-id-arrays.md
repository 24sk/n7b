## この記事の結論

「商品IDのハードコード配列を3ファイルに手動追記する運用」を、「S3に画像があるかどうかを`<img>`のonloadで判定する運用」に置き換えた設計判断の記録です。読み終わると、なぜ配列廃止の方が壊れにくいのか、AWS障害時のフォールバックをどう設計に織り込むか、という 2 点が持ち帰れます。

舞台は EC-CUBE 系の EC サイト。サイクル図(お届け間隔の説明画像)を表示するために、3 つの JS ファイルに同じような商品 ID 配列が並んでいる、という典型的な負債の話です。

## 何が起きていたか

該当ページには `#product_image` という空の `<img>` タグが置いてあり、購入確認画面・スキップ LP・完了オファーの 3 画面それぞれで、別々の JS が「今表示している商品 ID が自分の配列に含まれていたら、画像 URL を差し込む」という同型の処理をしていました。

配列は約 360 件。新商品を追加するたびに、担当者は 3 つのファイル全部に ID を追記する必要がありました。実際にログを追うと、3 ファイル間で配列が乖離しており、6 件の商品でサイクル図が出ていない画面がすでに存在していました。ファイル名の指す運用が「登録簿」になってしまっていたわけです。

画像自体は自社 AWS の S3 + CloudFront に `id{商品ID}.webp` という決まった命名で置かれています。つまり **命名規則さえ守られていれば、配列を持たなくても存在するかどうかは URL を叩けば分かる** 状態でした。

## 配列を廃止して onload/onerror に任せる

採用した方針はシンプルです。JS からは配列を消し、次のように書き換えます。

```js
const img = new Image();
img.onload = () => showCycleImage(img.src);
img.onerror = () => { /* 何もしない */ };
img.src = `https://belta-shop.bbo-tech.com/confirm/id${productId}.webp`;
```

デフォルトの HTML には従来通り「標準のお届けサイクル表」が描画されており、`#product_image` は非表示。画像の取得に成功したときだけ、表を隠して画像を出す、という **上書き型** のレンダリングにしました。

メタファーとしては「壁に貼るポスター」に近いです。ポスターがあれば貼る、無ければ壁紙(標準の表)がそのまま見える。ポスターの一覧表(配列)を別途管理する必要はなく、ポスター束(S3 バケット)そのものが台帳を兼ねます。

## AWS 障害時のフォールバックはどこにあるか

設計中に届いた良い問いが「S3 に障害が起きたらどうするのか」でした。答えは「フォールバックはすでに構造の中にある」です。

CloudFront が応答しない場合、`Image` は `onerror` を発火するか、そもそもロードが完了しません。どちらにせよ **表示切替は起きない** ので、閲覧者には最初から描画されていた標準テーブルが見えたままになります。「S3 が落ちない前提だから省略している」のではなく、「落ちても壊れないから追加処理が要らない」という順序です。

これは配列方式では実現できなかった性質でもあります。旧方式では、配列に ID があるのに画像がアップされていない場合、`<img>` が壊れたアイコンで露出していました。新方式は失敗を「無表示」に閉じ込められます。

## つまずきポイント: 命名規則が新しい単一障害点になる

配列を消した代償として、**ファイル名の付け間違いが即障害** になります。`ID1385.webp` (大文字始まり) や `id-1385.webp` (ハイフン付き) を上げても、画像は表示されません。旧運用では「JS 配列への追記」が登録の意思表示だったのに対し、新運用では「命名そのものが登録」に変わるためです。

対策として運用ドキュメントに以下を明記しました。

- 命名は `id{商品ID}.webp` 固定 (例: ID 1385 → `id1385.webp`)
- アップ後、`https://belta-shop.bbo-tech.com/confirm/id{商品ID}.webp` を必ずブラウザで開いて表示確認する

技術的な単一障害点を減らすと、代わりに運用ルールの厳格さが要求される、という古典的なトレードオフです。ここは図解で新旧フローの差分を運用者に渡し、削れる作業と厳守すべき作業を分けて共有しました。

## まとめ

- ハードコード配列は「登録簿の二重管理」になりがちで、乖離した瞬間に静かに壊れる
- `onload`/`onerror` で存在チェックする方式は、AWS 障害時にも「無表示」に閉じるためフォールバックが構造に組み込まれる
- 代わりに命名規則が新しい契約点になるので、運用ドキュメントと表示確認手順で担保する

次は、この画像アップロード自体を Playwright ではなく HTTP クライアントで自動化する検証に進みます。
