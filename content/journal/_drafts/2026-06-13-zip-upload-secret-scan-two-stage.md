## この記事のゴール

スキル共有プラットフォーム「skedachi」で、ユーザーがアップロードする ZIP に API キーやパスワードが紛れ込まないようにする仕組みを、今日 Claude Code と一緒に組みました。やったのは「ユーザーに同意させる UI 層」と「ZIP の中身を実際に走査するサーバー層」を二段で重ねる設計です。

この記事を読むと、以下が分かります。

- フォーム側のチェックボックスだけでは不十分な理由
- サーバーで ZIP を展開してスキャンするときの、検出時のフロー設計 (止める / 警告して再送信)
- Nuxt UI v4 の `UModal` を使った「警告 → 了承して公開」の往復実装の勘所

## フォーム側: 同意なしでは送信させない

最初に組んだのはフォーム側のガードです。公開ボタンの直前に投稿ガイドライン (機密情報を含めない / 第三者の権利を侵害しない) を箇条書きで置き、その下に `UCheckbox` で同意チェックを 1 つ。

肝は Zod スキーマ側で `agreed: z.literal(true)` にしておくことです。`boolean` ではなく `literal(true)` にすると、`false` のままだとそもそもフォームバリデーションが通らない。チェックを外したまま「公開する!」を押しても、ボタンが沈黙する設計になります。

ただし、これは「気をつけて読んでもらう」ためのレイヤーで、悪意や事故を止める力はありません。クライアントの JS を介さず API を直接叩けば素通りしてしまうからです。

## サーバー側: 同意フラグ必須 + ZIP 中身を走査

次にサーバー側を二段重ねにしました。

1. アップロード API で `agreed` フラグを必須化 (フォームと同じ条件をサーバーでも検証)
2. `parseSkillZip` が展開済みエントリを返すようにして、`secret-scan.ts` で中身を機械的にチェック

スキャンの中身は、API キーらしき文字列・秘密鍵ヘッダ (`-----BEGIN ... PRIVATE KEY-----`)・`.env` っぽいキー=値ペアなどを正規表現で拾うシンプルな実装です。

ここで設計上の分かれ道がありました。検出したら **完全に弾く** か、**警告して了承を求める** か。skedachi のスキルは「コードと一緒に config サンプルを置くこと」が普通にあるので、誤検知を 0 にはできません。そこで後者にしました。

## 「警告 → 了承して公開」の往復フロー

フローはこうです。

1. クライアントは普通に POST する
2. サーバーが検出したら 422 で「警告リスト」を返す (ファイル名:行番号と種別だけ。平文は載せない)
3. クライアントは `UModal` で警告を表示し、「了承して公開」ボタンを出す
4. ユーザーが押したら `acknowledgeSecrets: true` を付けて再送信
5. サーバーはスキャンをバイパスして公開するが、`console.warn` に「誰が何件了承して公開したか」を残す

レストランの「アレルギー表記を確認しましたか?」の確認に近い構造です。情報は渡す、最終判断はユーザー、ただし誰がいつ判断したかは店側に記録が残る。

レスポンスに平文を載せない (`file:line (種別)` だけ) のは地味ですが大事で、警告レスポンス自体が二次漏洩の入り口にならないようにする配慮です。

## つまずいたところ: 監査ログをどこまでやるか

レビューで「`acknowledgeSecrets=true` で API を直叩きすれば素通りでは」という指摘が出ました。確かにその通り。対応として、了承公開のときも **スキャンは走らせる** ようにして、検出があれば `console.warn` で件数と種別だけログに残す形にしました。

本来は専用の監査テーブルを切るのが筋ですが、まずはログレイヤーで「誰かが何かを了承して通したという事実」が残る状態にして、永続化は次のスコープに回しています。引き算の優先度付けはこの手の機能では特に効きます。

## まとめ

- ZIP アップロードの機密チェックは「フォーム同意」と「サーバースキャン」の二段にし、サーバー側も `agreed` 必須にする
- 検出時は弾かず、警告レスポンス → モーダル → 了承して再送信、の往復で運用上の現実とすり合わせる
- 警告レスポンスには平文を載せず、了承公開時はログに痕跡を残す

次は、ログに留めている了承記録を監査テーブルに昇格させるかどうか、運用しながら判断します。
