## この記事のゴール

「AI にコードレビューをやらせる」と一言で言っても、実際に社内で回すには報告書・チェックリスト・配布・呼び出し方まで通す必要があります。この記事では、N7B が今日構築・記事化した社内ツール `belta-review` の設計を振り返りながら、**過去の障害を AI レビューの燃料に変える** ための最小構成を書き残します。読み終わると、自分のチームで似た仕組みを組む際の「登場人物」と「つなぎ方」が見えるはずです。

## 起点は「障害報告書」というただのテキスト

出発点は Notion に溜まっている障害報告書でした。これを AI レビューの燃料にするには、報告書のまま渡しても長すぎて使い物になりません。そこで挟むのが **チェックリスト化** という一段の変換です。

流れはこうなります。

1. 障害報告書を書く (人間)
2. AI が「次に似た障害を防ぐには、コードのどこを見ればよいか」を箇条書きに要約する
3. 人間が承認して、社内の全リポジトリに配る
4. 開発者は PR を出す前に「BELTA 観点でレビューして」と Claude Code に頼む

報告書は物語、チェックリストは物語から抽出した「見るべき点」のリスト。レゴの説明書に近いイメージで、完成品 (障害の再発防止) をどう組むかの手順だけを残します。

## 配布は SKILL.md というただのファイル

仕組みの中心にあるのは `SKILL.md` という Markdown ファイルです。Claude Code は起動時にリポジトリ内の `skills/*/SKILL.md` を読み込み、そこに書かれた手順を「呼び出せるスキル」として扱います。

平たく言うと、**AI に対する社内マニュアル** をリポジトリに置いておくだけで、`/code-review` のようなスラッシュコマンドとして全員が同じ手順を呼べるようになる、という仕掛けです。

N7B の運用ではさらに、PR 作成手順を書いた `create-pr/SKILL.md` の中に「PR を作る直前に `/code-review` を実行し、指摘があれば直してから push する」というステップを明文化しました。ここが今日の後半の作業で、**手順書に書いていない運用ルールは半年後に必ず消える** という経験則への対処です。人間の記憶ではなく、AI が毎回読むファイルに書く。

## つまずいたのは「認証と配布の順番」

実装より地味に効いたのは、記事を sukedachi (社内ナレッジ基盤) に投稿するときの MCP 認証でした。ヘッドレスな Claude Code セッションからはブラウザ認証を通せないため、対話版 CLI で一度 `/mcp` を実行してサーバーを認証し、その後の新しいセッションでようやく `upload_knowledge` が使える、という順序を踏む必要があります。

もう一つ学んだのは、**チェックリストは全リポジトリに機械的に配る前提で設計する** ということ。1 箇所だけ手で貼ると必ず古いバージョンが残ります。GitHub Actions で定期的に同期する側に振り切ると、「更新したのに一部のチームに届いていない」という事故が消えます。

## まとめ

- 障害報告書は AI レビューの燃料。ただし報告書のままではなく、チェックリストに変換して配る
- 配布経路は `SKILL.md` に集約し、PR 手順書の中に呼び出しステップを明文化する
- 対話版 CLI での MCP 認証を先に済ませてから、自動投稿のセッションに移る

次は N7B の他のリポジトリにも同じスキルを配って、`/code-review` が本当に日常語になるかを試します。
