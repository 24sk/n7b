## この記事のゴール

サービスを閉じる作業は、作る作業より難しい場面があります。動いているものを止め、コストの発生源を全部消し、他のプロジェクトを壊さない。この 3 つを同時に成立させる必要があるからです。

今日 N7B は、社内で運用していた LP 監視サービスを丸ごと閉鎖しました。AWS の CloudFormation スタック 20 個、Vercel プロジェクト、CDK リポジトリ内の LP 専用コード 78 ファイル。作業を通じて見えてきた「サービス閉鎖の作法」を、順番に書き残します。

読み終えたときに持ち帰ってほしいのは、次の 3 点です。閉鎖は「止める → 消す → 検証する」の順で進める。関連リポジトリの掃除は本番作業と分離してブランチを切る。IaC (コードでインフラを管理する仕組み) の外にあるリソースは必ず手で探す。

## 止める、消す、検証する

最初にやったのは、動いているものを止めることでした。LP-Monitor は EventBridge (AWS の定期実行スケジューラ) で 1 時間に 13 回 Lambda を起動していたので、削除前にこのルールを無効化しました。実体を消す前に「呼び出し口」を閉じるのがコツです。呼び出し口が開いたまま裏側を消すと、実行中のジョブがエラーを吐き続けて監視ノイズになります。

次に Vercel プロジェクトを削除し、CloudFormation スタックを依存の浅い順に Wave 1 (Lambda・IAM 系)、Wave 2 (DynamoDB・S3 系) と 2 波に分けて削除しました。Wave 1 で 2 スタックが失敗したのですが、原因は「IAM ユーザーに手動で追加されたインラインポリシー」でした。CDK で作ったユーザーに、後から手で権限を足していたのです。

これが今日一番の学びでした。**IaC の外で足された設定は、IaC の削除に必ず引っかかる。** 家具付き物件を退去するときに、自分で買い足した棚だけ残って鍵が返せない状況に似ています。

## リポジトリの掃除は本番作業と分離する

AWS 側が片付いた後、CDK リポジトリから LP 専用コードを削除する作業に入りました。ここで一度立ち止まったのが、作業していたブランチに別プロジェクト (CSDB 連携) の未マージコミットが 3 件乗っていたことです。

このまま main にマージすると、閉鎖作業と進行中の機能開発が同じ PR に混ざります。何か問題が起きたときに切り分けができません。そこで次の手順を踏みました。

1. 進行中の作業を `git stash` で退避する
2. main ベースの新ブランチを切って、閉鎖コミットだけを `cherry-pick` で移す
3. 分離ブランチで型チェックと `cdk synth` (CDK の設定検証コマンド) を通す
4. PR を切ってマージ
5. 元のブランチに戻って `stash pop` で作業を復元

レゴブロックの箱を 2 つ用意して、混ざったパーツを 1 個ずつ正しい箱に入れ直すイメージです。手数は増えますが、混ざったままより圧倒的に安全でした。

## つまずき — IaC 管理外のリソースが残る

削除完了と思った後、ドキュメントに残っていた Secrets Manager (AWS の秘密情報保管庫) の ARN を辿ったら、CDK 管理外の Secret が 1 つ残っていました。過去に手動で作られたものです。

CloudFormation スタックを全部消しても、スタック外で作られたリソースは残ります。閉鎖の最後には「サービス名で AWS 全体を grep する」工程を必ず入れる、と手順書に追記しました。

## まとめ

- サービス閉鎖は「呼び出し口を止める → 実体を消す → 名前で全リージョン検索」の順で進める
- 閉鎖コミットは進行中の機能開発と別ブランチに分離してからマージする
- IaC の外で作られたリソースは必ず残るので、最後に手で探す

次に閉じるサービスが来たら、この 3 点をチェックリスト化して最初に机の横に貼ります。
