## この記事のゴール

GitHub の issue に `@claude` とコメントすると Claude Code が実装してくれる、あの仕組み。動くはずのワークフローが「起動はしているのに 1 ターンで落ちる」状態にハマったときに、どう切り分けたかの記録です。

結論から先に置きます。Claude Code Action が **370ms・課金ゼロ・num_turns=1** で失敗するときは、YAML でもモデル ID でもローカル設定でもなく、**API キー層 (認証エラー) を最初に疑うのが最短ルート**でした。以下、その辿り方を残します。

## 起きたこと

ある組織で、あるリポジトリの issue に `@claude` を書いてもワークフローが動かない。別のリポジトリでは動く。同じ caller ワークフロー (呼び出し元の共通 YAML) を使っているのに挙動が違う、という状態でした。

ログを開くと、動いた側のリポジトリでも実は失敗していました。しかも落ち方が独特です。

```json
{
  "model": "claude-opus-4-8",
  "is_error": true,
  "num_turns": 1,
  "total_cost_usd": 0
}
```

CLI の初期化までは走っている。モデル ID もログに載っている。なのに 370ms でエラー、課金はゼロ。issue には「Claude encountered an error after 0s」とだけコメントが残る。

## 対照群で切り分ける

こういうときは「動くリポジトリと動かないリポジトリを並べて、違いを 1 つずつ潰す」のが早いです。料理でいえば、同じレシピで作ったのに味が違うとき、材料を一つずつ入れ替えて確かめるやり方に近いです。

最初の仮説は「YAML の `with:` ブロックがコメント行だけになっていて、実キーが 0 個 → null 扱いで弾かれているのでは」でした。組織内の caller を 4 つ並べると、`with:` に実キーがあるリポジトリはワークフロー名が `Claude Code` としてパースされ、コメント行だけのリポジトリはパスがそのまま名前になっていました。相関 4/4。

ただ、これは「起動できるかどうか」の話であって、「起動した後に 370ms で死ぬ」現象とは別レイヤーでした。ここで一度立ち止まって、症状を分けます。

- レイヤー A: そもそもワークフローが起動しない → YAML パース問題
- レイヤー B: 起動はするが 1 ターンで死ぬ → API 層問題

今回のメインは B です。

## 「課金ゼロ」が指す先

`total_cost_usd: 0` は強いヒントでした。Anthropic の API に 1 回でも通っていれば、失敗しても最小トークン分は乗るはずです。ゼロということは、**API に到達する前か、認証段階で拒否されている**。

候補は 2 つに絞れます。

1. リポジトリ内の `.claude/settings.json` などローカル設定でコケている
2. GitHub の Organization Secret に入っている API キーが古い / 失効している

1 は実物を確認して除外しました。`PostToolUse` フックしか登録されておらず、これはツール実行後に発火するもの。1 ターン目で死ぬ今回の症状には絡めません。

残ったのが 2。Secret の更新日を見ると数ヶ月前。手元で確認したキーの残高は $25 残っていましたが、**「残高があるキー」と「Secret に入っているキー」が同一とは限らない**。ローテーション後に Secret 側を差し替え忘れると、401 で即死・課金ゼロという、まさに今回のシグネチャになります。

## つまずいたポイント

途中、API キーの直接検証で `curl -H "x-api-key: YOUR_KEY"` をそのまま流してしまい、`invalid x-api-key` を「キーが失効している証拠」と読みかけました。実際は `YOUR_KEY` という文字列を送っただけで、本物のキーについては何も検証できていない。

プレースホルダを実キーだと勘違いする、というのは自分では起きないと思っていた種類のミスでした。履歴に残さないよう `read -rs` で受け取り直して再検証、という手順に落ち着きました。

## まとめ

- Claude Code Action が「370ms・課金ゼロ・1 ターン」で死ぬときは、YAML より先に API キー層 (Secret の中身) を疑う
- 動く / 動かないリポジトリを並べて、レイヤー (起動 / 実行) を分けて切り分けると早い
- `curl` でキーを検証するときはプレースホルダを実値だと勘違いしないよう `read -rs` で受け取る

次のアクション: Organization Secret のキーをローテーション後の値で上書きして再実行する。
