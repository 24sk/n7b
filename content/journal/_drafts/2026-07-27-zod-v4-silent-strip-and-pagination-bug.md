## 「もっと見る」を押しても同じ 12 件が積み上がる

この記事は、記事一覧の「もっと見る」ボタンが壊れていた話を追いかけたログです。結論から書くと、原因はクライアントとサーバーで**ページング指定のキー名がずれていた**こと、そしてそれを黙って通してしまう **zod v4 のデフォルト挙動**でした。フォームやクエリのバリデーションに zod を使っているプロジェクトなら、同じ地雷を踏み得ます。ここで拾える教訓は 1 つ、「スキーマにないキーは、エラーではなく沈黙で消える」ということです。

## 症状: 押しても押しても同じ記事たち

記事一覧は 12 件ずつ読み込み、末尾の「もっと見る」で追加ロードする作りです。テスト記事を 16 件用意して押してみると、件数は 12 → 24 → 36 と増えるのに、**中身は全部同じ 12 件**。しかも `hasMore` が永遠に true のままで、ボタンが消えません。

最初はフロントの重複排除ロジックを疑いました。けれど DevTools の Network タブで API レスポンスを見ると、2 回目のリクエストも 1 ページ目と同じ配列を返しています。サーバーが同じものを返しているのだから、フロントで排除しても意味がない。原因はサーバー側にありました。

## 原因: zod v4 は未知キーを黙って捨てる

クライアントは `?offset=12` を送っていました。一方、`/api/articles` の zod スキーマはこう書かれています。

```ts
const querySchema = z.object({
  page: z.number().optional(),
  limit: z.number().optional(),
})
```

受け付けるのは `page` だけ。zod v3 の頃、オブジェクトスキーマは既定で「不明キーを許容し、そのまま残す (passthrough)」振る舞いでした。v4 になってからは**不明キーを黙って削除**します。エラーにはならず、ログにも出ません。レゴブロックで例えるなら、設計図に載っていないパーツを箱に入れると、検品係が何も言わずにゴミ箱へ捨てていく、そんなイメージです。

結果、サーバーが受け取るクエリは `{}`。`page` は未指定なので既定値の 1 が使われ、いつまでも 1 ページ目が返る。`hasMore` は「返した件数 === limit」で判定していたので、常に `12 === 12` で true。無限に「もっと見る」が続く仕組みが完成していました。

### 直し方は 2 か所

- クライアントの composable を `page` を送る形に統一する
- サーバー側でページ番号ベースにオフセットを計算し直し、`hasMore` は「まだ後ろに記事があるか」で判定する

これで 12 → 18 件、重複ゼロ、最終ページでボタンが消える動きになりました。

## 学び: 沈黙するバリデーションを疑う

今回の厄介さは、バグが「エラーを吐かない」ところにありました。テストは通り、ログもきれい、サーバーは 200 を返す。全部正常に見える。それでも UI だけが壊れている。

zod v4 のように「未知キーは黙って捨てる」設計は、API の入り口を狭く保つには理にかなっています。ただ、**クライアントとサーバーで契約がずれた瞬間、無症状のまま動き続ける**副作用があります。対策としては、

- クエリパラメータの型定義をクライアント/サーバーで共有する (`z.infer` を両側で使う)
- 開発モードだけでも `.strict()` を付けて未知キーをエラーにする
- E2E で「2 ページ目の中身が 1 ページ目と違うこと」まで確かめる

このうち一番効くのは、たぶん `.strict()` を dev 時だけ有効にする運用でした。本番で壊すと困るので envで切り替える形が現実的です。

## まとめ

- 「もっと見る」で同じ記事が繰り返される原因は、`offset` と `page` のキー名ずれだった
- zod v4 は未知キーをエラーではなく沈黙で削除するため、契約ずれが無症状で残る
- 対策は型共有・dev 時 `.strict()`・2 ページ目までの E2E 検証

次は、開発モードだけ `.strict()` に切り替える薄いラッパーを用意して、他の API にも横展開してみます。
