## 今日の問い: 旧DBから新DBへのインポート機能、どこに置く?

運用者から「旧DBから新DBにデータをインポートする機能が欲しい」と相談を受けた日です。データ変換ロジック自体は Laravel 側にコマンドとして実装済み。足りないのは「運用者が押せる実行ボタン」だけ、という状況でした。

この記事で扱う結論は1つです。**スキーマの migrate と データの import は、見た目が似ていても別物として実行経路を分けたほうがいい**。理由はシンプルで、トリガーの性質が違うからです。push で勝手に走っていいものと、人間が意思を持って実行するものを、同じ仕組みに混ぜると事故ります。

## 似て非なる2つの「DB操作」

既存のシステムには、すでにスキーマ migrate を自動化する GitHub Actions が動いていました。`deploy-stg-db.yml` という名前で、ブランチに push されると統合DBにトンネルを張って `php artisan migrate` を実行する、よくある構成です。

今回追加したい import は、コマンドとしてはよく似ています。`php artisan import:all` のような形で、旧2つのDB (cs_db / cs_admin) から読み出し、外部キー依存順に統合DBへ書き込む。一見、既存ワークフローにステップを1つ足せば済みそうに見えます。

しかし中身を覗くと、性質がまったく違いました。

- **migrate**: 接続先は統合DB 1本。push されたら自動で走っていい。失敗してもスキーマ変更が止まるだけ。
- **import**: 接続先はソース2本 + 統合DBの計3本。push で勝手に走られると、コードを直すたびに旧データが流れ込む。実行タイミングは人間が決めるべき。

レシピで例えると、migrate は「冷蔵庫の棚板を組み替える」作業、import は「他所の冷蔵庫から食材を運び込む」作業です。前者は決まったタイミングで自動化していい。後者は「いつ運ぶか」を人間が判断しないと、まだ準備できていない棚に生鮮品が積まれることになります。

## 採用した実行経路

そこで、import 用には別ワークフローを新設する方針にしました。ポイントは2つです。

### トリガーは `workflow_dispatch` のみ

GitHub Actions には push や schedule など複数のトリガーがありますが、import-data.yml には**手動実行 (`workflow_dispatch`) だけ**を残しました。push トリガーは意図的に書きません。「書かない」ことを設計として明示します。

これで、運用者は Actions 画面の「Run workflow」ボタンから、環境 (stg) と対象テーブルを選んで実行する形になります。逆に言えば、誰かが import コマンドのコードを直して push しても、データは1行も動きません。

### 権限とネットワーク経路は infra 側で増設

既存のデプロイロールは「統合DB 1本にトンネルする」前提で組まれていたので、ソース2DB への到達経路と Secret 読取権限を CDK 側に追加しました。具体的には Secrets Manager のエントリ2本、セキュリティグループ2本、IAM の grantRead を2行。最小権限を保つため、既存ロールを書き換えるのではなく、必要な分だけ足す形にしています。

## やってみて気づいたこと

設計を Claude Code と詰めていく中で、相談相手から「必要な時のみ動く仕組みか、push のたびに動くのか」という質問が来ました。これは実装者から見ると当たり前の前提でも、運用者目線では真っ先に不安になるポイントです。

ここで気づいたのは、**「migrate と import の違い」を表で並べて見せると一発で伝わる**ということ。やること、トリガー、接続先DB、失敗時の影響範囲を縦軸にして横並びにすると、なぜ別ワークフローにするかが言葉の説明より早く腹落ちします。設計ドキュメントを書くときは、似ているものほど表で差分を可視化する価値があると改めて感じました。

もう1つの学びは、Notion の親ページ配下にサブページとして実装タスクを切り出す効果です。親ページには方針と全体像、子ページにはチェックボックス形式の手順。粒度を分けると、依頼者は方針だけ追い、実装者は手順だけ追えるようになります。

## まとめ

- 似たコマンドでも、トリガーの性質が違えば実行経路を分ける
- import は `workflow_dispatch` のみにして、push で勝手に走らせない
- 差分を伝えるときは表で並べると早い

次は同じ設計を本番環境に展開するときの承認フローを詰めていきます。
