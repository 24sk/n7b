## この記事のゴール

Notion のページを起点に GitHub Issue を自動起票するワーカーで、`AI_Repository` プロパティに指定したリポジトリが完全に無視され、常に既定のリポジトリへ誤起票される不具合が出ていました。原因は Notion API のスキーマや権限ではなく、TypeScript 側でプロパティ値を取り出す関数の書き方でした。

この記事を読むと、`??`(Nullish 合体演算子) を連鎖させるときに三項演算子を混ぜると何が起きるか、そしてなぜ「型ごとに順に候補を試す」ヘルパーが壊れやすいかが分かります。1 記事 1 バグの深掘りです。

## 事象: url 型だけが常に空になる

発端は、Notion のあるページから起票された Issue が、指定していたリポジトリ (仮に `repo-A` とする) ではなく、既定の別リポジトリ `repo-B` に立っていたことでした。ページを見に行くと `AI_Repository` プロパティには `https://github.com/.../repo-A` が入っています。Notion API のレスポンスも確認したところ、`AI_Repository` の型は `url`、値も正しく取れていました。

一方で、同じページの `AI_依頼者` (text 型) や `AI_Claudeモデル` (select 型) は正常に反映されていました。text と select は読めて url だけ読めない、という偏った症状です。

## 原因: `??` 連鎖に三項演算子を混ぜていた

該当のヘルパーはこんな形をしていました (再現用に整理したもの)。

```ts
const value =
  prop.select?.name ??
  prop.status?.name ??
  (prop.rich_text?.length ? prop.rich_text[0].plain_text : "") ??
  prop.url ??
  "";
```

一見「select → status → rich_text → url の順に試して、どれかにヒットしたらそれを返す」ように読めます。実際はそう動きません。

問題は 3 行目の三項演算子です。`rich_text` が空配列や undefined のとき、この式は `""` (空文字) を返します。そして `??` は **null と undefined のときだけ** 右辺に進む演算子です。空文字は「値がある」と判定されるため、そこで連鎖が止まり、`prop.url` の行には一生たどり着かないのです。

メタファーで言えば、駅伝のランナーが「持っていなければ次に渡す」ルールなのに、途中のランナーが「空っぽの袋」を持って走り切ってしまう状態です。袋の中身は空でも、袋そのものは存在するのでバトンは渡されません。

## 修正: `undefined` を返すか、if で分岐する

直し方はシンプルです。ヒットしなかったときは空文字ではなく `undefined` を返すようにします。

```ts
const richText = prop.rich_text?.[0]?.plain_text;
const value =
  prop.select?.name ??
  prop.status?.name ??
  richText ??
  prop.url ??
  "";
```

これで `rich_text` が空のときは `undefined` になり、`??` が正しく次の候補へバトンを渡します。最後の `?? ""` はデフォルト値としての空文字なので、こちらは残して構いません。

## 学び: フォールバック自体もリスクになる

修正後にコードレビューを回したところ、別の観点が挙がりました。「そもそも `AI_Repository` に値があるのに解析できないケースで、既定リポジトリへ黙ってフォールバックしていいのか」という指摘です。今回のように読み取り側のバグでフォールバックが発動すると、誤起票が静かに続きます。ログは出ていたものの、警告レベルでは気づかれにくい。

「安全側に倒すためのフォールバック」が「バグを覆い隠す仕組み」に化けることは珍しくありません。値の解決に失敗したら起票自体を止める、あるいは Notion 側にエラー状態を書き戻す、といった強めの分岐を入れるほうが健全です。

## まとめ

- `??` 連鎖の途中に「空文字を返しうる式」を挟むと、そこで連鎖が止まって以降の候補に到達しない
- 型ごとにプロパティを試すヘルパーは、ヒットしなかったら `undefined` を返す設計にする
- 既定値へのフォールバックは、読み取りバグを覆い隠す方向にも働く。失敗時は止める判断も選択肢に入れる
