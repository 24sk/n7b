## この記事で分かること

スキーマ (DB の設計図) に「NOT NULL の新カラム」を追加する変更を、複数の Claude Code セッションが並行して走っている状況でどう安全に進めたか、という一日の記録です。読み終えると、Git worktree を作業隔離に使うコツと、Drizzle が自動生成した SQL を「壊れない順序」に手編集するときの考え方が分かります。

今日 N7B が触っていたのは、ワークフローの「工程 (step)」からスキル紐付けを任意にする改修でした。DB のカラム構造から実行系のプロンプト組み立てまで縦断する変更です。ここでは実装内容ではなく、進め方の工夫だけを切り出します。

## 並行セッションと worktree 隔離

作業を始めた時点で、同じリポジトリの共有 checkout 上に、別テーマの未コミット変更が 2 ファイル残っていました。N7B の変更ではありません。ここに直接ブランチを切ると、pull や lint のたびに他人の変更を巻き込むリスクがあります。

そこで `.claude/worktrees/` 配下に専用の作業ツリーを作り、`feat/workflow-step-title-optional-skill` ブランチを隔離しました。Git worktree は、平たく言うと「同じリポジトリの別フォルダにもう一つ作業場を開く」機能です。レゴブロックで言えば、同じ箱から取り出したブロックを別の作業マットの上で組み立てるようなイメージです。ベースは共有しつつ、途中経過は互いに干渉しません。

隔離のおかげで、`pnpm install` を worktree 側で改めて走らせる手間はあったものの、その後の編集は他セッションと完全に分離できました。

## 絶対パスで踏んだ落とし穴

ここで一度つまずきました。エディタに渡した編集指示の絶対パスが、worktree ではなく親リポジトリを指していたのです。せっかく隔離したのに、schema.ts の変更が親側に入りかけました。

気付いた時点で親側のファイルを元に戻し (残す差分は他セッションの 2 ファイルのみと確認)、worktree の絶対パスに書き直して適用し直しました。学びとして、worktree で作業するときは「操作対象のルートパスを一度変数化して常にそこから組む」くらいの明示性が要ります。相対パスに頼ると、どのシェルの cwd で解釈されるかで結果がずれます。

## 生成 SQL を「壊れない順序」に書き直す

もう一つの山は、`db:generate` が吐いた SQL の手編集でした。Drizzle は schema の差分から素直に `ADD COLUMN "title" text NOT NULL` を生成します。空のテーブルなら問題ありませんが、既存行があると NOT NULL 制約に引っかかって失敗します。

対処は 3 段階に分けるだけです。

1. まず NULL 許容で `ADD COLUMN` する
2. 既存行に既定値 (例えば紐付いていたスキル名) を `UPDATE` で埋める
3. 最後に `ALTER COLUMN ... SET NOT NULL` に切り替える

朝のラジオ体操の手順表と同じで、順番を守れば誰がやっても同じ結果になります。生成 SQL をそのまま流すのではなく、「本番の既存行が通るか」を頭の中でリプレイしてから確定するのが習慣として要ります。

編集後に `db:generate` を再実行し「No schema changes」と出ることで、schema と SQL のズレがないことを確認しました。ここが緑にならないと、次回の generate で差分が復活します。

## まとめ

- 並行セッションが動くリポジトリで破壊的変更を触るときは、worktree に隔離するだけで事故率が下がる
- worktree では絶対パスの起点を明示的に固定し、操作先が親か子かを毎回確認する
- NOT NULL カラム追加は「追加 → 埋める → 制約付与」の 3 段階に手編集し、`db:generate` の再実行で差分ゼロを確認する
