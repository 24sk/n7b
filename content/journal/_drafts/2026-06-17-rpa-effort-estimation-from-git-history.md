## この記事のゴール

「RPA の改修って、1 件あたり平均どれくらいかかるんですか?」という問いに、感覚ではなく Git 履歴の実測で答える方法を残します。N7B は今日、3 つの RPA リポジトリ (合計 887 コミット) を Claude Code に読ませて、89 改修・平均 3 人日／件という数字を 1 セッションで叩き出しました。

この記事を読み終えると、手元の社内リポジトリでも同じ手順で「改修 1 件あたりの人日」を弾き出せるようになります。見積もり根拠を聞かれて言葉に詰まる場面の、ひとつの処方箋として読んでもらえれば。

## 「1 改修」をどう定義するかが 9 割

最初にぶつかった壁は、改修の単位がリポジトリごとにバラバラだった点でした。あるリポジトリは PR ベース、別のリポジトリは直 push 中心、さらに別のは GitLab 管理でそもそも PR が無い。`gh pr list` だけでは全体を捕まえられません。

試行錯誤の末に行き着いたのが、**feature ブランチ名のチケット ID (例: `DEV-OM-123`) を改修の単位とする** という割り切りです。チケット = 1 改修、というレゴブロックのような最小単位を決めると、PR の有無に関係なくコミットを束ねられるようになりました。

```bash
# ブランチ名からチケット ID を抽出して改修を数える
git log --all --format='%H %s %D' \
  | grep -oE 'DEV-[A-Z]*-[0-9]+|DB1-[0-9]+' \
  | sort -u | wc -l
```

この「単位の定義」が決まると、あとは機械的に集計するだけです。

## 規模別に分けて二極構造を可視化する

89 改修を一律に平均すると、実態を見誤ります。実際に集計してみると、変更行数と稼働日数で綺麗に三つの山に分かれました。

| 区分 | 件数 | 平均稼働日 | 推定工数／件 |
| --- | --- | --- | --- |
| 小 (パラメータ修正・バグ fix) | 27 | 1.0 日 | 0.5〜1 人日 |
| 中 (機能改修・処理追加) | 39 | 2.3 日 | 2〜3 人日 |
| 大 (新規ロボット実装) | 23 | 6.1 日 | 5〜8 人日 |

面白いのは、74% の改修は 3 人日以内で終わっているのに、26% の新規実装が平均を押し上げているという二極構造が見えてきたこと。「平均 3 人日」とだけ言うと中規模改修のイメージを連想させますが、実際は「ちょい修正」と「がっつり新規」の混ざり合いです。見積もりを伝えるときは、この内訳ごと渡したほうが事故が減ります。

## つまずきポイント: STG と本番の二重マージ

途中で数字が膨らんで首を傾げた瞬間がありました。マージコミットを単純に数えると、改修件数が実態の倍近くになる。原因は、運用上 **STG 版と本番版で同じ改修が 2 回マージされる** ワークフローでした。

これをチケット ID 単位に寄せて重複排除し、各チケットの「最大稼働日数」「最大変更行数」だけを採用することで、ようやく実態に近い数字に落ち着きました。Git の数字をそのまま信じず、運用フローを 1 枚剥がして確認する手順は省略できないところです。

もうひとつの学びは、**図に書かれた構成と実装が一致しないことがある** という当たり前の事実。今回も、依頼元の構成図には「ネクストエンジン」「ロジザード WMS」と書かれていたのに、実コードを grep すると 0 件。実態は別の SaaS で実装されていて、図は To-Be 構成だった、というオチでした。見積もりの精度を上げる作業は、半分はこういう「図と実装のズレを暴く」作業になります。

## まとめ

- 改修の単位は PR ではなく **feature ブランチのチケット ID** で揃えると、リポジトリ横断で集計しやすい
- 平均だけでなく **小／中／大の三層に分けて** 渡すと、見積もりが現実とズレにくい
- Git 履歴の数字は **運用フロー (STG・本番の二重マージなど) を考慮して** 補正する
