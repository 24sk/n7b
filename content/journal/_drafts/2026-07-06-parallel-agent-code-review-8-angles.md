## この記事で分かること

この記事は「PR レビューを Claude Code の並列エージェント (複数の下請け AI を同時起動する仕組み) に任せたら、設計書だけと言われた PR からカットオーバー当日に本番を落とす級の欠陥が 3 件見つかった」という体験記です。読み終える頃には、レビューを 1 本の視線で流すのではなく「観点ごとに独立した目玉を並べる」やり方の手触りが掴めるはずです。

対象は Laravel のあるリポジトリの、DB 正規化 PR。差分は migration 12 本 + seeder 3 本 + 506 行のインポートコマンド。PR 説明には「ドキュメントのみ」と書かれていましたが、蓋を開けると本気のコードが入っていました。

## 8 つの観点を同時に走らせる

レビューは code-review スキルを起点に、以下の観点でエージェントを並列起動しました。

- 規約 (CLAUDE.md) レビュー
- 効率の観点
- 単純化の観点
- 再利用の観点
- 高度 (設計深度) レビュー
- Angle A: 行単位スキャン
- Angle B: 削除挙動監査
- Angle C: クロスファイル追跡

イメージとしては、1 枚の図面を 8 人の職人に同時に渡し、それぞれ「配管だけ」「電気だけ」「動線だけ」と担当を分けて見てもらう感覚です。人間が 1 人で全部見ようとすると、途中で疲れて後半の観点がおざなりになりますが、独立したエージェントに切り出せば、どの観点も同じ濃度で最後まで走ります。

並列起動が終わると、それぞれのファインダー (発見担当) が指摘を吐き出します。ここで終わらせず、次に「検証エージェント」を別途立てて、指摘 1 件ずつに対して「本当にそのコードでその挙動が起きるか」を実コードで裏取りさせました。ファインダーは疑い深く、検証は冷静に、と役割を分けたわけです。

## 出てきた「本番を落とす級」の 3 件

検証パスまで通した結果、CONFIRMED が 10 件、補足が 4 件残りました。特にマージ前に潰すべきは次の 3 点でした。

1. **メールアドレスの未正規化**: 移行先の customers テーブルには大文字小文字を区別しない unique index が張られているのに、インポート側は生の文字列を突っ込む設計。旧データに `Foo@example.com` と `foo@example.com` が混在すると、メンテ枠中にインポートがクラッシュします。
2. **ゼロ日付ガードの適用漏れ**: `form.time` などの列に `0000-00-00` 相当が残っており、MySQL の strict mode で SQL エラーになる。ガード関数は存在するのに、掛け忘れの列がありました。
3. **`verifyCounts` が不一致でも exit 0**: 移行後の件数照合が失敗しても、コマンドは成功扱いで終わる。CI やジョブランナーから見ると「移行成功」に見えるまま、次工程 (カットオーバー) が進んでしまいます。

1 と 2 は「動かしてみれば分かる」タイプですが、本番相当のデータでリハーサルしないと踏まないやつです。3 に至っては、動かしても静かに壊れるタイプで、レビューで捕まえないと現地で気づけません。

## つまずいた点: セッション上限とバックグラウンド落ち

並列で走らせると当然トークンを食うので、途中で「session limit」に何度もぶつかりました。さらに、あるバックグラウンドエージェント (Angle A: 行単位スキャン) は親プロセスが終了したタイミングで巻き添えになり、in-process の状態が失われて failed で戻ってきました。

学びは 2 つ。並列度は「同時に必要な観点数」ではなく「セッション予算で走り切れる本数」で決めること。そして、長時間走るバックグラウンド処理は、親を落とさない前提で組むか、途中経過をファイルに落とす前提で組むこと。今回は failed になった観点だけ後追いで再起動して埋め直しました。

## まとめ

- 「1 人で全部見る」レビューを「観点ごとに独立エージェント」に分解すると、後半の観点まで濃度が落ちない
- ファインダーと検証を別レイヤーにすると、指摘の空振りが減って本当に踏むバグだけが残る
- 並列度はセッション予算で決める。バックグラウンド処理は親プロセス依存を避ける

次は、この 8 観点セットをスキル化して、他リポジトリの PR にも同じ手順で流し込めるように整えます。
