## この記事で分かること

コードの中に「保険」として書かれた選択肢リストが、いつの間にか「仕様書の一次情報」として扱われてしまうことがあります。今日 N7B は、40 個ほどある Notion データベースの列名について、その保険リストをそのまま仕様書に転記していたことに気づき、実測で剥がしました。結論は 2 つです。

- **保険は「まだ揺れている」という主張を暗黙に含む**。実測で揺れがないと分かれば、消したほうが変更検知が効く
- **実測は Notion API を叩くより、GCS に落とした raw JSON を集計するほうが早い**

## きっかけは仕様書の表記揺れ

仕様書に、こんな列名の記載がありました。

- Cost / コスト / 広告費 / cost
- 表示回数 / IMP / インプレッション / Impressions
- クリック / CLICK / クリック数 / Clicks

一見「Notion 側でこれだけ表記が揺れているのだな」と読めます。ところがコードを追うと、これは `DEFAULT_PROPERTY_MAP` という「候補リスト」でした。パイプラインは先頭から順に探し、最初に見つかった名前の値を採ります。つまり **「どれが来ても拾えるようにしてある保険」** です。

仕様書はこの保険リストを一字一句そのままコピーしていました。読み手からすれば「揺れている事実の記録」に見えるのに、実際は「揺れているかもしれないという可能性の記録」だったわけです。

メタファーで言えば、傘立てに 4 本の傘が置いてあるのを見て「今日は雨・曇り・雪・晴れが混在する日」と天気予報を書いてしまった状態です。傘は「どの天気でも対応できるように」置いてあるだけで、実際の天気は 1 つしかありません。

## GCS の raw JSON を数えるだけで済んだ

実測の手段として最初に思いつくのは Notion MCP で 40 個の DB を 1 つずつ取りにいくことです。ただ、これは重い。既に毎朝 Notion からダンプして GCS に保存しているので、そちらを集計すれば済みます。

```
gs://belta-notion-growth-reports/raw/dt=2026-07-29/
```

ここに置かれた JSON を全走査して、各行の properties キーを集計しました。結果、取り込み済み 36 DB は **列名セットのパターン数が 1**。つまり完全一致。残りの 3 DB（BigQuery に未取り込みだったプレリズム系）も Notion API で直接確認し、同じ 17 列でした。

**揺れは 1 件もなかった。**

それが分かれば、保険は害になります。列名が変わったときにフォールバックが黙って別の候補を拾い、値が null にならずに済んでしまうからです。実名 1 本にしておけば、変更時は確実に `emptyMetrics` 警告が出て気づけます。

## つまずき: 「保険」の削除だけでは終わらなかった

実測ついでに、プレリズム配下だけ Notion のページ構造が違うことも見つかりました。中間ページ「■媒体別詳細レポート」が挟まっていて、クローラのページング処理を通り抜けられていなかったのです。BigQuery に 1 件も入っていなかった原因はこれでした。

さらに META 系は「合算 DB ＋ 内訳 DB 2 つ」の構成で、内訳まで `ad_type=合算` と判定されて二重計上寸前でした。

実測して初めて、こういう「構造の例外」が見えます。列名の揺れを確かめにいったつもりが、副産物としてデータ欠落と二重計上の原因まで芋づるで出てきました。**保険を剥がす作業は、剥がした瞬間に隠れていた構造を露出させる**、と言えます。

そして得た事実は、コードのコメントだけでなく `.claude/memory/notion-report-layout-variants.md` として「正本」に残しました。次に同じ調査をする人（半年後の自分を含む）が、また 40 DB を数え直さずに済むように。

## まとめ

- 保険としてのフォールバックリストは、実測前は仕方ないが、実測後は害になる（変更検知が効かなくなる）
- 実測の一次情報は Notion API より、既に GCS に落ちている raw JSON を集計するほうが早い
- 実測で見つかる副産物（構造の例外・二重計上・データ欠落）は本題より重いことがある

次のアクションは、他の「保険リスト」も同じ手順で棚卸ししていくことです。
