# /breakdown — タスク分解

引数: `$ARGUMENTS`

## あなたのゴール

入力ドキュメント (または会話文脈) を読み込み、**実装可能な最小単位**のタスクに分解し、チェックリストとして `docs/tasks/<basename>.md` に保存する。

## 手順

### 1. 入力ソースの確定

- `$ARGUMENTS` が**ファイルパス**の場合 (例: `docs/foo.md`、`/abs/path/bar.md`、または読める拡張子で終わる文字列):
  - そのファイルを `Read` で読む。複数ファイルが指定された場合はすべて読む
  - 出力ファイル名は最初の引数の basename を使う (例: `docs/設計.md` → `docs/tasks/設計.md`)
- `$ARGUMENTS` が**空**または**自由文の指示**の場合:
  - これまでの会話文脈をソースとして扱う
  - 出力ファイル名はユーザーに確認する (slug を提案する形でよい)
- `$ARGUMENTS` に**指示の修飾**が含まれる場合 (例: `docs/foo.md の Phase 2 だけ`):
  - ファイルパスを抽出してそのファイルを読み、スコープを指示に絞る

### 2. 内容把握と不明点の確認

ドキュメントを読んだ上で、**タスク分解前に**不明点があれば `AskUserQuestion` で確認する。典型的な不明点:

- スコープの範囲 (全体か、特定 Phase / セクションだけか)
- 既存 `docs/tasks/tasks.md` 等と重複する内容の扱い (再掲 / 参照 / 除外)
- 外部サービス・アカウント準備のような「実装」とは別軸のタスクを含めるか
- 出力ファイル名 (既存ファイルがある場合は上書き確認)

**不明点が無いなら質問しない**。推測で足りる箇所を都度確認するのは避ける。

### 3. 最小タスクへの分解

1 タスク = 1 PR、もしくは 30〜90 分で完了できる粒度を目安にする。判断基準:

- **粒度**: 「Stripe SDK 導入」「Pinia ストア設計」のように責務が 1 つに絞れる単位
- **検証可能性**: そのタスク単独で動作確認 (Lint / typecheck / 画面確認 / curl 等) ができる
- **依存の明確さ**: 依存タスクが完了していれば着手できる
- **分割しすぎない**: 「ファイル作成」「import 追加」レベルまで割ると逆に管理コストが上がる

### 4. 出力フォーマット (既存 `docs/tasks/tasks.md` 踏襲)

```markdown
# <ドキュメントタイトル> 実装タスク

<1〜3 行の概要。何を作るためのタスク一覧か、参照元ドキュメントへのリンク>

## 前提・制約 (任意 / あれば)

- 箇条書きで方針メモ・運用上の制約を記す

---

## <大分類: Phase X / Aセクション など>

### <中分類: Week N / サブテーマ>

- [ ] **ID-1** タスクのタイトル + 1 行説明
- [ ] **ID-2** 別のタスク  
  依存: ID-1
- [ ] **ID-3** さらに別のタスク (複数依存)  
  依存: ID-1, ID-2

> **方針メモ**: セクションごとに補足が必要なら引用ブロックで残す

---

## マイルストーン (任意 / フェーズ分割がある場合)

- **<節目>**: <達成状態>
```

書式ルール:

- ID は **大分類のプレフィックス + 連番** (例: Phase 1 → `1-1`, `1-2` / セクション A → `A-1` など)。元ドキュメントが連番を持っていれば踏襲する
- チェックボックスは必ず `- [ ]` (未着手)。既に完了しているとユーザーが明示した分だけ `- [x]`
- 依存関係は `  依存: ID, ID` をタスク行の直下に**2 スペース + 改行 2 つの行末スペース**で続ける (既存 tasks.md と同じ書式)
- 実装順は基本的に**上から下へ実行できる順序**で並べる。ただし依存のない並行作業は同じセクション内にまとめてよい
- セクション区切りは `---` (3 ハイフン)
- 関連ドキュメントへの参照は `@docs/...` 形式または相対パスで貼る

### 5. 保存と確認

- 保存先は `docs/tasks/<basename>.md` (basename は入力ファイル名の拡張子前)
- 既存ファイルがあれば上書き前にユーザーに確認する
- 保存後、生成タスク数とファイルパスを 1〜2 文で報告する
- `docs/tasks/tasks.md` のような大元タスクリストの**更新は行わない**。新規ファイルとして独立させる (必要なら手動で統合する)

## 守るべきこと

- **元ドキュメントに書かれていないタスクを勝手に追加しない**。推測で「テストも追加すべき」など足さず、元の指示に忠実に分解する
- **タスクの責務を 1 つに絞る**。「A して B もする」と書きたくなったら 2 タスクに分ける
- **検証手段が無いタスクを作らない**。手段が思いつかなければ別タスクに依存させて吸収するか、検証コマンド/確認方法を 1 行添える
- 出力前に `Read` で `docs/tasks/tasks.md` をざっと確認し、既存 ID と衝突しない命名にする
